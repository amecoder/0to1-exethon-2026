# 라이너 .EXE-THON 2026 — 신청 주제와 구현 범위

- 참가 확정: 2026-11-12 (운영팀 메일)
- 개발 기간: 11-12(목) ~ 11-25(수), **제출 마감 11-25 23:59 KST** (마감 후 불가)
- 결선 진출 8팀 발표 11-27(금), 결선·시상 12-05(토) 라이너 본사
- 공식 페이지: https://contests.liner.com/hackathon/exe-thon-2611/
- 출처: 0절은 신청서 「경험」·「구현 계획」 칸 문장(사용자가 2026-11-12 공유). 1~3절은 그 전에 ChatGPT와 논의한 정리본(같은 날 공유)
- **기준 우선순위**: 0절 신청서 문장이 정본이다. 1~3절과 다르면 0절을 따른다

## 0. 신청서 문장 (정본)

### 경험 (문제)

> 소프트웨어 개발 프로젝트를 진행하면서 담당자마다 BRD, PRD, 화면설계서, 테스트 케이스 등 개발에 필요한 문서에 대한 이해도와 작성 역량이 달라 산출물의 품질 편차가 큰 문제를 반복적으로 경험했습니다.
>
> 요구사항이 불명확하거나 문서 간 내용이 일치하지 않고, 예외 조건이나 완료 기준이 누락되는 경우가 많아 개발자가 매번 문서를 검토하고 피드백해야 했습니다. 특히 요구사항이 변경될 때마다 관련 문서를 다시 확인하고 누락되거나 충돌하는 내용을 찾아야 해 기획자와 개발자 모두 반복적인 검토와 수정 작업에 많은 시간을 소비하고 있습니다.
>
> 이러한 문제를 해결하기 위해 AI 에이전트를 활용해 담당자가 표준화된 문서를 작성할 수 있도록 지원하고, 문서 간 정합성, 요구사항 누락 및 변경 영향을 자동으로 검증하여 개발 초기 단계부터 산출물의 품질을 높이고 싶습니다. 나아가 AI 코딩 에이전트가 검증된 문서를 기반으로 요구사항을 정확하게 이해하고 구현할 수 있도록 하여, 기획부터 개발·테스트까지 이어지는 전체 소프트웨어 개발 프로세스의 생산성과 품질을 개선하고자 합니다.

### 구현 계획

> 담당자가 개발하려는 서비스의 목적과 요구사항을 입력하거나 기존 문서를 업로드하면, AI 에이전트가 내용을 분석하고 부족하거나 모호한 부분을 질문하여 요구사항을 구체화합니다.
>
> 확정된 요구사항을 바탕으로 BRD, PRD, 화면설계서, 테스트 케이스 등 개발에 필요한 문서를 표준화된 형식으로 작성하고, 문서 간 정합성, 누락된 조건, 상충하는 내용 등을 자동으로 검증하여 개선안을 제시합니다.
>
> 기획자, 개발자, QA 등 각 담당자가 문서를 검토하고 피드백할 수 있는 협업 환경을 제공하며, AI 에이전트는 피드백을 분석해 수정안을 제안합니다. 각 담당자의 검토 및 승인(Confirm)을 거쳐 요구사항과 명세를 최종 확정하고, 승인 이력과 의사결정 근거를 관리하여 모두가 동일한 기준으로 개발을 진행할 수 있도록 합니다.
>
> 이후 요구사항이 변경되면 관련 문서와 테스트 케이스에 미치는 영향을 분석하고 수정안을 제안하며, 필요한 담당자의 재승인을 거쳐 문서 간 일관성을 유지합니다.
>
> 최종적으로 검증·승인된 문서를 AI 코딩 에이전트가 활용할 수 있는 구조화된 명세로 제공하여, 요구사항 분석부터 구현과 테스트까지 연결되는 소프트웨어 개발 프로세스의 생산성과 품질을 높입니다.

### 정리본(1~3절)에 없고 신청서에만 있는 것

- 입력 경로 2가지: 목적·요구사항 **직접 입력** 또는 **기존 문서 업로드**
- 승인 이력과 함께 **의사결정 근거**를 관리
- AI가 담당자 **피드백을 분석해 수정안**을 제안
- 변경 시 **필요한 담당자만** 재승인

## 1. 해결하고 싶은 문제 (Why)

소프트웨어 개발 산출물의 품질 편차와 요구사항 관리의 비효율성.

- 담당자마다 BRD, PRD 등 문서 작성 역량과 이해도가 다름
- 요구사항의 모호함, 누락, 문서 간 불일치가 반복됨
- 개발자가 기획 산출물을 반복적으로 검토하고 수정 요청해야 함
- 요구사항 변경 시 영향 분석과 관련 문서 수정이 수작업으로 이루어짐
- 불완전한 명세가 AI 코딩 에이전트에 전달되면 잘못된 구현으로 이어질 수 있음

해결 방향: AI로 요구사항 분석·문서 작성·검증을 표준화하고, 개발 초기부터 명세의 품질을 확보한다.

## 2. 에이전트가 해 줄 일 (What)

| # | 기능 | 흐름 |
|---|---|---|
| ① | 요구사항 수집 및 구체화 | 목적·요구사항 입력 → 모호한 조건 질문 → 명세 구체화 |
| ② | 표준 문서 생성 | BRD · PRD · 화면설계서 · 테스트 케이스 |
| ③ | 문서 정합성 및 품질 검증 | 누락 · 충돌 · 예외 조건 · 완료 기준 검증 |
| ④ | 담당자 협업 및 승인 | 기획자 · 개발자 · QA 피드백 → 수정 → 승인 및 이력 관리 |
| ⑤ | 변경 영향 분석 및 재승인 | 변경된 요구사항 → 영향 추적 → 관련 산출물 갱신 |
| ⑥ | AI 코딩 에이전트 연계 | 검증·승인된 구조화 명세를 개발·테스트에 활용 |

## 3. 차별점 (정리본의 주장)

문서 자동 생성 자체가 아니라, 검증과 사람의 승인을 거쳐 신뢰할 수 있는 개발 명세를 확정하는 과정.

1. **검증 가능성** — AI가 만든 산출물도 요구사항·문서 간 정합성을 검증한다
2. **사람의 판단 유지** — AI는 수정안을 제시하고, 최종 확정은 담당자가 한다
3. **추적 가능성** — 요구사항·산출물·테스트 케이스·승인 이력·변경 영향이 서로 연결된다

정리본의 범위 제안: 6개 기능을 같은 깊이로 만들지 말고 **요구사항 구체화 → 문서 정합성 검증 → 담당자 승인 → 변경 영향 분석**을 하나의 완결된 흐름으로 구현한다. (MVP 범위는 아직 확정 전)

## 4. 대회가 정한 제약 (운영팀 메일·공식 페이지)

- **Liner Model API 또는 Liner Search API/MCP 중 하나 이상을 핵심 기능에 사용** (필수)
- 크레딧 $200, 11-12 18시 이후 지급. API 키는 `platform.liner.com`에서 발급
- API 키는 `.env` 등 환경 변수로만 읽는다 — 심사 때 운영팀 키로 바꿔 실행
- 회사 내부 문서·영업비밀·고객 정보·개인정보 사용 금지 → 시연 데이터는 가상 데이터 또는 공개 데이터
- 출품작은 대회 기간에 새로 만들었거나 기존 결과물을 크게 발전시킨 것. 기존 결과물을 바탕으로 했다면 기존/신규 부분을 README·기획서에 구분
- 신청서에 등록한 팀원만 개발
- 심사 기준(예선·결선 공통): 문제 정의, 완성도, Liner API 활용, 확장성과 파급력
