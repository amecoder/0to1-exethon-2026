## 0. 한 줄 정의

발주사(사람)가 말로 던진 요구를 **7개 에이전트 팀**이 질문 카드로 구체화하고, **ID가 붙은 공유 원본 하나**에서 BRD·PRD·화면설계서·테스트 케이스를 만든 뒤, **사람이 중간 지점마다 컨펌한 기록**이 있어야만 다음 단계로 넘어가 웹 프로토타입까지 만드는 에이전트 팀 작업대.

## 1. BRD

### 1-1. 문제 (사용자 답변 원문 — 초안 8절)

| 사용자 말 | 이 제품에서의 뜻 |
|---|---|
| "말이 **기록으로 안 남고 요구사항 명세도 안 남아서**, 나중에 담당자가 '아 이거 아닌데?' 하면 검증할 수 없고 작업이 끝나지 않는다" | 핵심 고통. 합의가 기록·명세로 남지 않아 완료를 검증할 수 없다 |
| "거의 모든 프로젝트에서 요구사항은 바뀌는데 일정은 안 바뀐다" | 변경이 기록·영향과 함께 남아야 "일정도 바뀌어야 한다"는 근거가 생긴다 |
| "요청 정리·회의록·문서 재작성으로 의견 확정까지 개발자가 한다" | 정리·문서화를 에이전트 팀이 맡는다 |
| "만들기 전에 모르는 것을 찾아가서 계속 묻는다" | 되묻기를 질문 카드로 앞당긴다 |
| "주로 회의 구두, 엑셀·워드·PPT, 지나가던 말, 이메일. 문장으로만 말해서 구체화가 어렵다" | 입력은 자유 문장. 구조화는 팀 몫 |

- 인용 가능한 외부 근거: NaPiRE 228개 조직 — 빠진 요구 48%, 소통 결함 41%, 요구 변경 33% (`docs/reports/2026-11-12_엑스톤_개발문서_구조와_독자이해_조사.md` 2절). 한국 통계·"수정 비용 100배"류는 쓰지 않는다(같은 문서 6절)

## 2. PRD

### 2-1. 사용자

| 사용자 | 정체 | 하는 일 |
|---|---|---|
| 발주사 | **사람**(앱을 실행한 테스터) | 첫 요구 입력, 질문 카드 답, 컨펌 4곳, 변경 요청, 결과 내려받기 |
| 소비자 | **에이전트** 페르소나(꽃 구독 고객) | 조율자 요청으로 화면설계서·프로토타입을 고객 관점에서 보고 불편·포기 지점을 남긴다 |
| 심사 운영팀 | 사람 | 저장소 복제 → `.env` 에 키 → 실행 → 시연 모드 재생 또는 실제 모드 입력 |

팀 에이전트 7개와 관계는 관계도 문서 1~2절 그대로다: 조율자 · FDE 리드 · 리서처(Liner Search) · PM·기획자 · 디자이너 · 개발자 · QA.

### 2-2. 시나리오 — 꽃집 「꽃님」 주 1회 정기구독 앱 (처음부터 끝까지)

| 단계 | 누가 | 일어나는 일 | 컨펌 |
|---|---|---|---|
| S1 입력 | 발주사 | 요청 메모(`request_memo.md`)를 붙여 넣는다. G3이 개인정보·비밀값을 검사, 원문은 고정 저장(G4) | |
| S2 문제 인식 | 조율자 → FDE 리드 ↔ 리서처 | FDE 리드가 "누가·무슨 불편·무엇이 완료인가"를 정리하고, 리서처가 Liner Search로 구독 서비스 관행(결제 실패·배송 실패 처리 등)을 출처와 함께 찾는다 | **CP1 문제·범위 컨펌** — 문제 진술, 범위 안/밖, 서울만·S/M 등 원문 해석 |
| S3 구체화 | 리서처 → PM, PM ↔ QA | PM이 요구 후보를 만들고 QA가 충돌·빠진 예외·완료 기준 없음을 지적 → 조율자가 질문 카드로 묶어 발주사에게 한 장씩. 예: "고객이 요일을 고르나요, 토요일에 한꺼번에 보내나요?" ① 고객이 고름 ② 토요일 일괄 ③ 수·토 중 고름 ④ 잘 모르겠어요 + 출처 | |
| S4 원본 확정 | 발주사 | 답이 반영된 REQ 목록(Given/When/Then, 상태: 확정/가정/미결)과 "가정" 모음을 본다 | **CP2 요구사항 원본 컨펌** → 버전 v1 고정 |
| S5 문서화 | PM ↔ 디자이너, PM ↔ QA, 소비자 | 디자이너가 화면설계서(SCR), QA가 테스트 케이스(TC), PM이 BRD·PRD 뷰. 소비자 에이전트가 화면설계서에 고객 의견을 남김. 조율자가 커버리지 빈칸(TC 없는 REQ 등) 검사 | **CP3 문서 4종 컨펌 = 개발 시작 승인** → 버전 v2 고정 |
| S6 개발 | 디자이너 ↔ 개발자, QA ↔ 개발자 | 개발자 에이전트가 단일 HTML 프로토타입 생성 → 격리 미리보기(G6). QA는 TC 기준으로 화면을 대조한 체크리스트만 남김(실행은 다음 단계) | **CP4 프로토타입 인수** |
| S7 내려받기 | 발주사 | HTML + 문서 4종(마크다운) + 공유 원본(JSON) zip | |
| S8 변경 (P1) | 발주사 → 조율자 | "일시정지는 배송 하루 전까지 되게 해 주세요" → 대상 REQ-06, 영향 SCR-02·TC-08·TC-09와 전후 비교. "아 이거 아닌데?"면 고정 버전과 대조해 **합의 위반 / 새 변경 요청** 구분 | **CP5 변경 반영 컨펌** → 새 버전 |

- 컨펌에서 발주사가 "아니요"를 고르면 사유를 한 줄 남기고 그 단계로 되돌아간다(조율자가 해당 에이전트에게 재작업 배정)
- 시연에서 발주사는 `owner_answers.md` 답하는 규칙(물은 것만 답, 없는 것은 "잘 모르겠어요")대로 답한다. 이 파일은 사람만 보고 **에이전트에는 절대 들어가지 않는다**

### 2-3. 기능 요구사항

우선순위: **P0** = 11-19 안전 제출본에 필요 · **P1** = 11-22 컷라인까지 · **P2** = PoC 뒤

| ID | 우선 | 요구 | 인수 조건 (Given / When / Then) |
|---|---|---|---|

### 2-5. 에이전트 정의 데이터 형식 (제안: `agents/<id>.json`, 팀은 `teams/<id>.json`)

### 2-6. 공유 원본 데이터 모델 (SQLite 저장, 내보내기는 JSON)

`requirements_fixture.json` 의 구조(`requirements[]` 의 `id/title/statement/depends_on/screens/tests`, `screens[]`, `tests[]`)를 **그대로 포함**하고 필드를 덧붙이기만 한다. 그래서 고정 정답표와 `eval/validate_golden.sh` 를 그대로 쓸 수 있다.

| 묶음 | 기존 필드 (fixture와 동일) | 덧붙이는 필드 |
|---|---|---|
| `requirements[]` | `id, title, statement, depends_on, screens, tests` | `acceptance`(given/when/then), `exceptions`, `status`(확정·가정·미결), `source_refs`(SRC-), `evidence_refs`(EV-), `decision_refs`(DEC-), `owner_agent` |
| `screens[]` | `id, title` | `elements`, `states`(빈·로딩·오류), `requirement_refs` |
| `tests[]` | `id, title` | `steps`, `expected`, `requirement_refs` |
| 새 묶음 | — | `sources[]`(원문 문장, 수정 불가) · `evidence[]`(Liner 질의·URL·인용문·원문) · `questions[]`(카드·선택지·답) · `decisions[]` · `open_items[]` · `confirmations[]`(CP 번호·누가·언제·버전·승인/반려·사유) · `versions[]`(스냅샷) · `events[]`(활동 기록, 시연 모드 재생 원천) |

- 영향 규칙은 fixture의 `impact_rule` 과 같다: 대상 REQ + depends_on 으로 전이적으로 기대는 REQ + 그 REQ들의 screens·tests
- 정합성 기준: 내보낸 JSON의 `requirements/screens/tests` 부분만 떼면 fixture와 같은 모양이어야 한다(테스트로 확인)

| **Liner Search API** | 리서처의 도구(툴 콜링). 질문 카드 선택지·기본값의 근거, 업종 흔한 예외(빠진 예외 탐지 근거), G1 출처 | 질문 카드·문서 문장 옆 출처, 활동 기록의 검색 질의 |

- 키: `LINER_API_KEY` 를 `.env` 에서만 읽고, 없으면 즉시 에러(CLAUDE.md 규칙 2)
- 시연 모드 재생은 Liner를 부르지 않는다. 대신 기록에 남은 실제 호출(모델·질의·출처)을 그대로 보여 준다
