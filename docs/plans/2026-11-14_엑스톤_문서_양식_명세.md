# 문서 4종 양식 명세 — 처음 보는 사람도, 전문가도 (컨펌 2026-11-14)

- 관련: `docs/plans/2026-11-14_엑스톤_PoC_BRD_PRD.md` FR-09(문서 4종 뷰)·2-6절(공유 원본) · 근거 `docs/reports/2026-11-12_엑스톤_개발문서_구조와_독자이해_조사.md`(앞선 조사), `docs/reports/2026-11-14_엑스톤_산출물_양식과_이해도_조사.md`(이번 조사)
- 이 명세는 **에이전트가 만드는 문서의 모양**이다. 에이전트 지시문과 화면(문서 탭)이 이 명세를 따른다

## 0. 원칙

| # | 원칙 | 근거 |
|---|---|---|
| P1 | **모든 문서는 두 층**: 맨 위 「한눈에 보기」(처음 보는 사람용, 5줄 이하 쉬운 말) + 그 아래 「상세 표」(전문가용, 표준 필드). 둘은 같은 원본에서 나온다 | 역할별 뷰(Gross & Doerr 2012, 앞선 조사 2절) · NIPA "수·발주자가 모두 명확하게 이해" |
| P2 | 상세 표의 필드는 **한국 공공 산출물 + 국제 표준**에서 가져온다. 우리가 지어낸 필드는 넣지 않는다 | NIPA 2021 · NIA 2011 · ISO 29148 · 29119-3 (이번 조사 1·2절) |
| P3 | 요구사항 ID 는 기존 `REQ-01` 형식을 유지하고, **분류 필드에 NIPA 접두어**(SFR·PER·SER·DAR·INR·COR 등)를 적는다 | 정답표·`requirements_fixture.json` 호환 + 한국 실무자가 아는 분류 |
| P4 | 화면설계서에는 **와이어프레임을 반드시** 넣는다 | 목업이 이해 정확도·효율을 크게 올림(Ricca 2014, 139명) — 이번 조사에서 가장 강한 근거 |
| P5 | 문서마다 **변경 이력**(버전·날짜·작성 에이전트·승인자 컨펌 ID)을 둔다 | NIA 공통 머리부 · 관계도 문서 G2 |
| P6 | 확인 안 된 것은 숨기지 않고 표시한다: 상태 「가정」「미결」, 사실 문장의 「미확인」 | 가드레일 G1·G5 · Spec Kit `[NEEDS CLARIFICATION]` |
| P7 | 가독성 지수는 쓰지 않는다. 쉬운 말 여부는 **규칙 검사**로 본다(5절) | Flesch 는 한국어에 맞지 않음, 가독성 점수 ≠ 이해도(이번 조사 3절) |
| P8 | 「한눈에 보기」는 **완전한 문장**으로 쓴다(글머리표 조각 금지). 상세는 표 (C6) | Amazon 서술형 메모 · Intercom "동료에게 마주 보고 설명하듯" (빅테크 조사) |
| P9 | 문서 맨 위에 **작성 책임 에이전트 1명과 승인 기록**(CF-)을 둔다 (C5) | Microsoft 기능 명세서 "작성자 1명" · Uber RFC "승인자 목록을 맨 위에" |
| P10 | **짧게**: BRD 본문 A4 2쪽 이하(제안). 넘으면 경고 — 넘친다는 것은 문제가 아직 덜 정리됐다는 신호로 본다 (C4) | Intercom A4 1장 · Amazon 6쪽 이하 · Linear "짧을수록 읽힌다" |

## 1. BRD — 왜 만드나 (제안요청서 앞부분에 해당)

| 순서 | 섹션 | 내용 | 원본 출처 |
|---|---|---|---|

## 2. PRD — 무엇을 만드나 (요구사항 정의서에 해당)

**구성**: 한눈에 보기(핵심 기능 5줄) → 요구사항 총괄표(분류별 개수, 상태별 개수) → 요구사항 상세 표 → **결정과 검토한 대안** → 열린 질문 → 변경 이력

- **결정과 검토한 대안** (C3, Google 설계 문서 "Alternatives considered"): 결정 기록(`DEC-`)에서 자동 생성. 한 줄에 결정 · 채택안 · 기각안과 이유 · 누가 답했나(질문 카드·컨펌 ID). 예: "DEC-03 일시정지 시점 — 채택: 주문 마감 전까지 / 기각: 언제든지(꽃을 이미 사 와서) — 발주사 답 Q-05"

**요구사항 상세 표 필드**

| 필드 | 뜻 | 출처 양식 | 원본 필드 |
|---|---|---|---|
| ID | `REQ-01` | NIPA ② · NIA R1 · 29148 식별자 | `id` |
| 분류 | SFR 기능 / PER 성능 / SER 보안 / DAR 데이터 / INR 인터페이스 / COR 제약 | NIPA ① | 추가: `category` |
| 이름 | 짧은 명칭 | NIPA ③ | `title` |
| 설명 | 한 문장. "무엇을", "어떻게"는 쓰지 않음 | NIPA ④ · 29148 5.2.7 | `statement` |
| 인수 조건 | Given / When / Then. **= 검수 기준** | NIA R1 검수기준 · ISTQB | `acceptance` |
| 예외 | 실패·예외 상황과 처리 | — (누락 결함 대응) | `exceptions` |
| 중요도 | 상 / 중 / 하 | NIA R1 · 29148 우선순위 | 추가: `priority` |
| 상태 | 확정 / 가정 / 미결 | P6 | `status` |
| 근거 | 왜 필요한가 + 출처 ID(`SRC-`·`EV-`) | NIPA ⑦ 출처 · 29148 rationale | `source_refs`, `evidence_refs` |
| 관련 요구사항 | 기대는 요구사항 | NIPA ⑥ | `depends_on` |
| 관련 화면·테스트 | `SCR-`·`TC-` | NIA D10 화면 ID · 추적성 | `screens`, `tests` |

## 3. 화면설계서 — 어떻게 보이나 (UI 설계서 + 한국 실무 스토리보드)

**구성**: 한눈에 보기(화면 흐름도 한 장) → 화면 목록 → 화면별 상세 1장씩 → 변경 이력

- **화면 목록**: 화면 ID(`SCR-01`) · 화면명 · 관련 요구사항 ID · 상태 (NIA D2)
- **화면 상세 (한 화면 한 장)**: 상단 화면명·ID / **왼쪽 와이어프레임(요소에 번호)** / 오른쪽 번호별 설명 표

| 번호 | 요소명 | 설명 | 동작과 결과 | 입력 규칙(타입·필수·검증) | 관련 REQ |
|---|---|---|---|---|---|

- 화면 상태: 빈 상태 · 로딩 · 오류 각각 한 줄 이상 (앞선 조사 · PRD 2-4절)
- 와이어프레임은 회색 상자 수준의 저충실도(실제 디자인 아님)로 생성한다 — 만드는 방법(SVG·HTML)은 구현 때 정한다

## 4. 테스트 케이스 — 됐는지 어떻게 아나

**구성**: 한눈에 보기("이럴 때 이렇게 되면 통과" 문장 5개) → 테스트 케이스 표 → 커버리지 표(REQ ↔ TC) → 변경 이력

| 필드 | 출처 |
|---|---|
| TC ID (`TC-01`) | 29119-3 식별자 · NIA D10/D11 |
| 목적 | 29119-3 objective |
| 관련 요구사항 · 화면 | 29119-3 추적성 · NIA D10 화면 ID |
| 우선순위 | 29119-3 |
| 사전조건 | 29119-3 · NIA D10 |
| 입력 (발주사가 읽을 수 있는 수준) | 29119-3 "수행자 지식에 맞춰" · NIA 입력자료 |
| 절차 | NIA D11 처리절차 |
| 기대 결과 | 29119-3 · NIA 예상결과 |
| 실제 결과 · 판정 | 29119-3 — PoC 에서는 빈칸(실행은 다음 단계) |

- 인수 조건 1개 → TC 1개 이상. 긍정 → 부정 → 경계 순 (ISTQB, 앞선 조사)

## 5. 품질 검사 — 두 독자 기준

**전문가 기준 (QA 에이전트 + 시스템 규칙, ISO 29148)**

| 검사 | 규칙으로 판정 | 기준 특성 |
|---|---|---|
| 한 요구사항에 한 가지 | 설명에 "그리고·및·또는"으로 이어진 서로 다른 동작이 둘 이상이면 경고 | singular |
| 모호어 없음 | 모호어 목록(빨리·적당히·가능한·등·충분히·편리하게…)이 설명·인수 조건에 있으면 경고 | unambiguous |
| 검증 가능 | 인수 조건(Given/When/Then)이 비어 있으면 경고 | verifiable |
| 빠짐없음 | 예외 칸이 빈 기능 요구사항, TC 없는 REQ, SCR 없는 REQ(사유 없을 때) | complete (묶음) |
| 서로 모순 없음 | 충돌 지적이 미해결이면 컨펌 불가 | consistent (묶음) |

**처음 보는 사람 기준 (규칙 검사 — 이해도를 직접 재지는 않는다)**

| 검사 | 규칙 |
|---|---|
| 한눈에 보기 있음 | 문서마다 5줄 이하 요약이 완전한 문장으로 있다 |
| 분량 | BRD 본문 A4 2쪽 이하(제안) — 넘으면 경고 |
| 용어 풀이 | 용어집에 있는 전문 용어가 처음 나올 때 괄호 풀이가 붙는다(풀이 누락 0) |
| 발주사 화면의 전문 용어 | 질문 카드·컨펌 화면 요약에 금지어(스모크 테스트 C3 목록과 같은 계열) 0개 |
| 원문과 해석 구분 | 발주사 원문 인용과 에이전트 해석이 다른 칸에 있다 |

- 한계: 위 규칙은 "이해했다"의 **대리 지표**다. 실제 이해도 측정(처음 보는 사람에게 읽히고 질문하기)은 근거 있는 방법이 요구사항 문서용으로는 없어서 PoC 에서 하지 않는다
