# 회사 작업 공간 설계 (2026-11-20)

## 0. 배경과 결정

- 사용자 요청(11-20): "SaaS 서비스를 제공한다고 봐봐, 각 가입자(회사)별로 문서 관리, 프로젝트도 관리해야해"
- 사용자 선택: **회사 구분 + 공통 자료** — 로그인 없이 회사 작업 공간을 고르고, 회사 공통 자료와 지난 프로젝트 결정을 새 프로젝트가 맥락으로 쓴다. 진짜 로그인·데이터 격리·역할 권한은 기획서에 설계로만 적는다(심사자가 계정 없이 실행할 수 있게)
- 지금 구조: `projects` 테이블 하나, 회사 칸 없음, 로그인 없음. 「우리 시스템 목록」은 프로젝트마다 다시 적는다(브라우저 localStorage 에만 기억)

## 1. 가설·검증

구현 전에 정한 가설과 판정 기준이다. H1 은 코드 테스트로, H2 는 Liner 실행 비교로 판정한다.

| 항목 | 내용 |
|---|---|
| 가설 H1 (구분) | 회사 A 에서 만든 프로젝트는 회사 B 의 프로젝트 목록에 나오지 않고, 회사 자료는 그 회사 프로젝트에만 들어간다 |
| 가설 H2 (맥락) | 같은 회사의 지난 프로젝트에서 확정한 결정이 회사 자료로 들어가면, 다음 프로젝트에서 같은 결정을 다시 묻는 질문 카드가 줄어든다 |
| 기준선 | H1: 지금은 회사 개념이 없어 측정 불가(목록에 모두 나옴). H2: 같은 요청 B 를 회사 자료 없이 돌렸을 때 「A 에서 이미 답한 주제를 다시 묻는 카드」 수 |
| 판정 기준 | H1: 단위·API 테스트로 다른 회사 목록 0건, 회사 자료 섞임 0건 — 하나라도 섞이면 기각. H2: 다시 묻는 카드가 기준선의 절반 이하 **그리고** 회사 자료로 정해진 지적 1건 이상 **그리고** 이번 요청과 무관한 회사 결정을 끌어다 쓴 경우 0건 — 하나라도 어기면 기각 |
| 측정 방법 | H1: pytest. H2: 같은 회사에 첫 프로젝트(결정 있음)를 두고, 같은 요청 B 를 (가) 빈 새 회사 (나) 같은 회사에서 S3 까지 각 2회 실행, 카드와 회사 결정 근거를 사람이 읽어 판정. Liner 비용이 들어 실행 전 사용자 승인 |

## 2. 범위

1. **회사 테이블**: `companies(id, name, created_at, systems, notes)`. `projects.company_id` 칸 추가. 기존 프로젝트는 「기본 회사」(`default`)로 옮긴다
2. **회사 자료**: 우리 시스템 목록(`systems`, 기존 형식 그대로)과 회사 공통 자료(`notes`: 용어, 사내 규칙, 이미 정한 것). 저장 전에 G3 민감 정보 검사
3. **지난 결정**: 같은 회사의 다른 프로젝트에서 발주사가 확정한 결정(대체되지 않은 것). 회사 화면에서 목록으로 본다
4. **새 프로젝트에 넣기**: 요구 입력(S1) 때 회사 자료를 `company` 항목(CMP-01…)으로 프로젝트에 복사한다. 나중에 회사 자료를 고쳐도 이미 시작한 프로젝트는 바뀌지 않는다(같은 입력이면 같은 결과)
5. **에이전트**: 질문 카드를 만드는 coordinator 만 `company` 를 읽는다(다른 에이전트는 단계마다 받는 자료가 정해져 있어 넣어도 닿지 않는다). 질문 카드 단계는 회사 자료로 답이 정해지는 지적을 카드로 만들지 않고 `settled` 에 적는다 → 코드가 확인한 것만 결정(`kind: company`, 확정, 근거 CMP-)으로 남기고, 미결로 넘기지 않는다
6. **화면**: 시작 화면에 회사 고르기·새 회사·회사 자료 편집. 프로젝트 목록은 고른 회사 것만. 요구 입력 화면의 시스템 목록은 회사 자료로 미리 채운다

## 3. 범위 밖 (기획서 「확장성」에 설계로)

- 로그인·계정, 회사별 접근 차단(지금은 프로젝트 주소를 알면 열린다), 발주사·팀원 역할 권한, 회사별 Liner 사용량·한도, 회사 자료 파일 업로드, 지난 결정 중 일부를 빼는 기능

## 4. 결과 (2026-11-20, 커밋 916c4ee)

H1 은 테스트로, H2 는 Liner 실행 4회로 판정했다. 측정 자료는 저장소 밖 `scratchpad/e2e5/`(drive.py, rounds.jsonl)에 있다.

- **H1 채택**: `tests/test_company.py` 14개 통과. 다른 회사 목록에 섞인 프로젝트 0건, 회사 자료는 그 회사 프로젝트에만 복사
- **H2 채택**: 같은 꽃집 예제 메모, 첫 질문 카드 회차까지. X = 「꽃님 플라워」(첫 프로젝트 `fe8439a4` 의 확정 결정 13건), Y = 빈 회사. 비용 $3.56 (잔액 113.57 → 110.00)

| 실행 | 회사 자료 | 지적 | 카드 | 회사 자료로 정한 지적 | 첫 프로젝트에서 이미 답한 주제를 다시 묻는 카드 |
|---|---|---|---|---|---|
| Y-1 | 0 | 22 | 8 | 0 | 3 (결제 시기, 마감 뒤 일시정지, 결제 실패) |
| Y-2 | 0 | 24 | 8 | 0 | 3 (결제 시기, 마감 뒤 일시정지·해지, 결제 실패) |
| X-1 | 13 | 23 | 8 | 7 | 0 |
| X-2 | 13 | 24 | 7 | 6 | 0 |

- 판정 규칙: 세 기준은 측정 전에 정했다. 다만 「다시 묻는 카드」를 가르는 세부 규칙(첫 프로젝트의 답 하나가 그 카드의 질문에 **바로** 답하는가)은 결과를 읽으면서 정했다. 그래서 비슷하지만 대상이 다른 것(예: 답은 「해지」, 카드는 「일시정지」)을 경계로 따로 셌다 — 경계까지 넣어도 Y 4·3, X 1·1 로 절반 이하다
- 기준 셋 모두 통과: 다시 묻는 카드 평균 3 → 0 (절반 이하), 회사 자료로 정한 지적 7·6건 (1건 이상), 주제가 다른 회사 항목으로 정한 경우 0건
- 관찰: 카드 수는 8 → 7.5 로 거의 같다. 회사 자료가 막아 준 자리에 새 질문(결제 7일 전 안내, 카드 취소 불가 환불, 구독 여러 개)이 들어왔다. 회사 결정의 답 중 일부는 회사 항목을 이번 지적에 맞게 풀어 쓴 것이다(예: 「이번 주 배송」 → 「집계와 알림에 포함」) — 틀린 적용은 아니지만 원문 그대로는 아니다
- 한계: 회당 2회, 메모 1종(첫 프로젝트와 같은 메모라 겹치는 주제가 가장 많은 조건). 다른 요청으로 이어지는 2차 프로젝트에서의 효과는 재지 않았다

## 5. 회사 온톨로지 1단계 — 이미 만든 서비스와 대조 (2026-11-20)

사용자 질문(11-20): "회사의 기존에 프로젝트, 서비스 등 이미 있는 프로젝트나 기능들이 있다면 그것들도 같이 확인해서 처리하는거야? … 온톨로지가 맞겠다는 생각이 들어". 사용자 선택: 측정(H2) 결과를 본 뒤 SQLite 로(그래프 DB 없음).

관계는 새 테이블 없이 기존 기록의 번호 참조에서 뽑는다: 회사 → 서비스(CP4 까지 확정된 그 회사 프로젝트) → 기능(확정·가정 요구사항) → 화면(SCR)·결정(DEC). 새 요청이 들어오면 서비스마다 「이름: 0to1로 만든 서비스 · 기능 …」 한 줄을 우리 시스템 목록에 더한다. 그러면 S2 의 기존 대조(기능 추가 / 연계 / 신규)와 요구사항의 `change`·`system_refs` 가 그대로 이 서비스를 가리킬 수 있다. 한 줄(300자)에 다 안 들어가면 Liner Rerank 가 요청과 가까운 기능부터 담는다(실패하면 원래 순서, fail-open).

| 항목 | 내용 |
|---|---|
| 가설 H3 | 같은 회사의 2차 요청에서, 1차 서비스가 시스템 목록에 들어가면 팀이 그 서비스에 「기능 추가·연계」로 잇고, 이미 있는 기능을 「신규」 요구사항으로 다시 만드는 경우가 줄어든다 |
| 기준선 | 같은 2차 요청을 빈 회사에서 돌렸을 때, 1차 서비스의 기능(20개)과 같은 일을 하는 요구사항 중 「신규」로 만든 것의 수 |
| 판정 기준 | 채택은 셋 다: (1) 두 실행 모두 S2 대조(system_fit)에 1차 서비스가 1건 이상 (2) 이미 있는 기능을 「신규」로 다시 만든 요구사항이 기준선 평균의 절반 이하 (3) 1차 서비스와 관계없는 요구사항을 그 서비스에 이은 경우 0건 |
| 측정 방법 | 2차 요청 메모 1종(가상: 정기구독 선물하기), 꽃님 플라워(X)와 빈 회사(Y) 각 2회, 첫 질문 카드 회차까지. 요구사항 후보의 `change`·`system_refs` 를 읽고, 「이미 있는 기능과 같은 일인가」는 사람이 1차 기능 목록과 대조해 판정. 비용 약 $3.5, 실행 전 사용자 승인 |

테스트: `tests/test_company.py` 19개(서비스는 CP4 확정 프로젝트만·같은 회사만, 한 줄 형식과 길이, 요구 입력 때 시스템 목록에 더해짐, Rerank 로 가까운 기능이 앞에 옴).

### 5-1. H3 결과 (커밋 a83acf5): 채택

가상의 2차 요청 「정기구독 선물하기」(scratchpad/e2e6/memo.txt)를 X = 꽃님 플라워(1차 서비스 「꽃님 정기구독」, 기능 20개), Y = 빈 회사에서 각 2회, 첫 질문 카드 회차까지 돌렸다. 비용 $3.43 (잔액 110.00 → 106.57). X 두 실행 모두 Liner Rerank 가 불렸다(기능 20개가 한 줄 300자를 넘음).

| 실행 | S2 대조에서 1차 서비스 | 요구사항 (신규 / 기능 추가·연계) | 이미 있는 기능을 「신규」로 다시 만든 요구사항 |
|---|---|---|---|
| Y-1 | 해당 없음 | 20 / 0 | 6 (서울 한정 배송 둘, S·M 사이즈, 일시정지, 배송 불가 처리, 주문 마감) + 경계 1 (카드 결제) |
| Y-2 | 해당 없음 | 16 / 0 | 5 (서울 한정, S·M 사이즈, 토요일 배송, 배송 불가 처리, 일시정지) + 경계 1 (카드 결제) |
| X-1 | 기능 추가 6건 | 0 / 16 | 0 |
| X-2 | 기능 추가 6건 | 0 / 18 | 0 |

- 기준 (1) 두 실행 모두 1차 서비스 대조 6건 — 통과. (2) 다시 만든 「신규」 평균 5.5 → 0 — 통과. (3) 1차 서비스와 관계없는 요구사항을 그 서비스에 이은 경우 0건 — 통과(모든 요구사항이 「정기구독 앱에 선물하기를 더한다」는 한 기능의 부분이다)
- 관찰: X 에서는 요구사항 전부가 「기능 추가」(X-1 은 1건 「연계」)로 바뀌었다. 기존 기능을 그대로 쓰라는 요구사항도 생겼다(「선물 배송에 기존 배송 규칙 적용」, 「기존 일시정지·재개를 받는 사람도」). 다만 X-1 「선물 배송지 서울 한정 검증」처럼 이미 있는 규칙을 다시 적은 것도 남아 있다 — 지금 분류(신규 / 기능 추가 / 연계)로는 「이미 있으니 그대로 쓴다」와 「그 앱 안에 새로 만든다」를 가를 수 없다
- 한계: 회당 2회, 2차 요청 1종(1차와 겹치는 기능이 많은 조건), 「같은 일인가」 판정은 사람(작성자) 1명

## 6. 회사 온톨로지 2단계 — 「재사용」 분류와 1차 기능 번호 (2026-11-20)

사용자 요청(11-20): "보인 한계를 개선하자, 확인 못한 것도 확인하자, 그리고 fable5.2로 적대적 리뷰해보자".

5-1절 한계는 「이미 있으니 그대로 쓴다」를 가를 분류가 없다는 것이었다. 바꾸는 것:

- 만드는 방식(`change`, S2 대조 `fit`)에 「재사용」을 더한다: 그 시스템에 이미 있어 새로 만들지 않고 그대로 쓴다
- 0to1 로 만든 서비스는 시스템 목록 항목에 `features`(한 줄에 담긴 기능, 번호는 `SYS-03/REQ-02` 처럼 시스템 번호를 앞에 붙여 이번 프로젝트의 REQ 번호와 섞이지 않게)를 붙인다
- 요구사항에 `feature_refs` 를 더한다. 코드는 그 요구사항이 가리킨 시스템의 기능 번호만 남긴다(없는 번호는 버림)
- AGENTS.md 작업 블록에 「재사용 — 새로 만들지 않는다 · 이미 있는 기능 SYS-03/REQ-02 …」를 적는다. 화면의 만드는 방식 배지에도 「재사용」이 보인다

| 항목 | 내용 |
|---|---|
| 가설 H4 | 「재사용」과 1차 기능 번호를 주면, 2차 요청에서 1차에 이미 있는 규칙을 다시 적은 요구사항이 「재사용」과 맞는 1차 기능 번호로 표시된다 |
| 기준선 | H3 의 X-1·X-2(같은 메모 A, 같은 회사): 재사용 0건(분류 없음). 이미 있는 규칙을 「신규·기능 추가」로 다시 적은 요구사항 수는 판정자가 센다 |
| 판정 기준 | 채택은 넷 다: (1) X 3회 모두 재사용 1건 이상 (2) 재사용 요구사항의 기능 번호가 맞는 비율 80% 이상 (3) 새로 만들어야 할 일을 재사용으로 단 것 0건 (4) 이미 있는 규칙을 재사용이 아닌 분류로 다시 적은 요구사항 평균이 기준선 평균의 절반 이하. 하나라도 못 넘으면 기각 |
| 측정 방법 | 메모 A(선물하기) X 3회, 첫 질문 카드 회차까지 |

5-1절 「확인 못 한 것」 세 가지도 같이 잰다:

| 항목 | 내용 |

- 스위치 `EXETHON_COMPANY=off`: `/api/features` 가 `{"company": false}`, 시작 화면에 회사 패널이 없고 전체 프로젝트를 보인다. 요구 입력에 회사 자료·지난 결정·만든 서비스·숨길 이름을 넣지 않는다. 제출 zip 은 원래 git 이 올린 파일만이라 DB(`data/`)가 들어가지 않는다
- 가명: 회사 이름(기본 회사 빼고), 회사가 적은 「Liner에 보내지 않을 이름」(약칭·브랜드, `companies.aliases`), 0to1 로 만든 서비스 이름을 S1(분류·첨부 읽기·요구 입력) 전에 정해 `meta.hidden` 에 둔다. Liner 호출 8곳(대화·검색·AI 검색·판정·재순위·시각화·이미지·첨부 읽기)이 감싼 클라이언트를 거쳐, 나갈 때 `XCORP1 …`(긴 이름부터), 돌아올 때 원래 이름으로 바뀐다. 저장·G1 인용 확인·문서는 원래 이름을 본다. 음성(받아 적기)은 소리라 바꿀 수 없다

| 항목 | 내용 |
|---|---|
| 가설 H8a | 스위치를 끄면 회사 자료가 있는 회사의 프로젝트에도 회사 것(CMP·서비스 줄·숨길 이름)이 하나도 들어가지 않는다 |
| 가설 H8b | 숨길 이름은 Liner 로 나간 요청에 0번 나오고, 저장된 결과에는 원래 이름이 남으며 가명이 남지 않는다 |
| 기준선 | 지금은 회사 이름·서비스 이름이 그대로 나간다(e2e9 Liner 기록에도 「꽃님」 4~8회). 선물하기(AX) 7회의 G1 걸림 0건, 저장된 XCORP 0건 |
| 판정 기준 | 테스트(`tests/test_hiding.py`)가 둘 다 통과하고, 실제 1회(메모 A, 꽃님 플라워, 숨길 이름 「꽃님」 추가)에서 (1) 첫 질문 카드 회차까지 오류 없음 (2) 나간 요청 전체에 「꽃님」 0번 (3) 저장된 결과에 XCORP 0개 (4) G1 걸림 0건 |
| 측정 방법 | 서버 대신 같은 앱을 스크립트 안에서 돌리며 나가는 요청을 모두 기록(`scratchpad/e2e10/run.py`). 비용 약 $0.8 |

### 7-1. 결과 (작업 트리, 커밋 전): H8a 채택 · H8b 채택

### 7-2. 기본값 꺼짐 (2026-11-20, 사용자 정정)

사용자 정정(11-20): "제출용에는 이전처럼 실제랑 시연만 동작하게 하려고 했지". 그래서 회사 작업 공간은 **기본 꺼짐**, `EXETHON_COMPANY=on` 일 때만 켜진다(심사 실행은 설정 없이 실제·시연만). 확인 서버 8100 은 `serve.sh` 에서 on 으로 띄운다. 테스트는 `tests/conftest.py` 가 on 으로 돌리고, 기본값은 `test_without_the_setting_the_company_workspace_is_off` 가 확인한다.

- 가설: 설정 없이 띄우면 `/api/features` 가 company false 이고 시작 화면에 회사 칸 없이 실제·시연 모드만 보인다. on 이면 지금과 같다
- 결과: 테스트 통과(pytest 669 · vitest 191). 회사가 여럿 든 DB 사본으로 설정 없이 띄운 8106 에서 `{"company":false}`, 시작 화면에 회사 칸 없음, 시연 모드 재생 화면 정상(`.playwright-mcp/company-off-start.png`, `company-off-demo.png`). 시작 화면은 설정을 읽기 전에도 꺼진 상태로 그려서 회사 칸이 깜빡이지 않는다
- 가명 치환(7절)은 회사 기능이 꺼져 있으면 숨길 이름이 없어 아무것도 하지 않는다
