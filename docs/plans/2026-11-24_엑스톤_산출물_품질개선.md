# 산출물 품질 개선 — 문서 사이 정합성과 읽기 쉬움 (2026-11-24)

0to1 이 넘겨주는 문서(BRD, PRD, 화면설계서, 테스트케이스, 제안요약, AGENTS.md, 묶음의 README.txt)를 고친다. 프로토타입은 범위 밖이다. 근거는 2026-11-23 평가(`docs/reports/2026-11-23_엑스톤_결과물_개발가능성_만족도_평가.md`)의 실패 유형 A(범위 축소가 뒤 문서로 안 퍼짐), B(집계가 사실과 다름), D(읽기 어려운 형식)이다. 유형 C(물어야 할 것을 안 물음)는 질문 단계를 바꾸는 일이라 이번에 하지 않는다.

이 문서의 1~3절은 코드를 고치기 전에 썼다. 4절은 고친 뒤 같은 방법으로 다시 재서 채웠다. 측정 규칙을 기준선 뒤에 손본 곳은 4-5절에 따로 적었다.

## 1. 측정 방법

입력은 평가에 쓴 묶음의 공유 원본 `scratchpad/bundle-eval/input/source.json` 하나로 고정한다. 문서는 제품의 렌더러(`app.export.bundle_files`)로 다시 만든다. Liner 호출은 없다.

### 1-1. 정합성: `scripts/measure_doc_consistency.py`

```
uv run python scripts/measure_doc_consistency.py <source.json> [--bundle-dir <폴더>] [--out <결과.json>]
```

규칙 네 가지로 위반을 센다. 모델을 쓰지 않는다.

| 검사 | 무엇을 위반으로 세나 |
|---|---|
| (a) 범위 | 화면 범위를 줄일 때 빠진 요구사항(`dropped_requirements`)이나 남기지 않은 화면의 ID 가, 「이번 범위에서 뺀 것」 절 밖에서 「(범위 밖)」 표시 없이 나온 줄. 빠진 화면으로 가는 요소를 그대로 그린 와이어프레임. 빠진 화면 위의 단계를 표시 없이 그린 레인 흐름도 |
| (b) 미결 수 | README.txt 의 「미결 N건」이 실제로 열려 있는 수보다 작다. 열려 있는 수 = 상태가 미결·미확인인 항목 + 미결 항목 + 숫자 기준이 없는 BRD 목표 + 본문에 「미정·빈칸·확인 필요·결정 필요·정해지지 않」이 남은 요구사항과 화면 요소 |
| (c) 연계 수 | 제안요약의 「연계 시스템 N개」가 요구사항·화면이 기대는 외부 서비스 수보다 작다. 외부 서비스는 낱말 목록(결제대행사·빌링키, 푸시, 주소 검색, 문자·알림톡, 로그인 제공자 등)으로 찾고, 「하지 않는다」처럼 부정하는 절은 세지 않는다 |
| (d) 없는 ID | 문서가 공유 원본에 없는 ID 를 가리킨다 |

### 1-2. 읽기 쉬움: `scripts/measure_doc_readability.py`

```
uv run python scripts/measure_doc_readability.py <source.json> --out <폴더>
```

도구는 hanlint 0.0.19(`--preset docs --disable dash`)다. 2026-11-24 에 잰 사실 두 가지 때문에 문서를 그대로 넣으면 거의 아무것도 안 걸린다.

- hanlint 는 표 칸 안의 글을 검사하지 않는다. 60어절 문장을 표 칸에 넣으면 `sectionNoProse` 하나만 나온다.
- 목록 항목과 인용문(`>`)도 검사하지 않는다. 같은 문장을 `- ` 뒤에 넣으면 지적이 0건이다.

그래서 「칸 사본」을 따로 만들어 검사한다. 25자 이상인 표 칸, 모든 목록 항목, 모든 인용 줄을 각각 한 문단으로 옮긴다. ID 만 나열한 칸(`REQ-01, TC-02 …`)은 문장이 아니라서 뺀다. 사본의 줄마다 원래 문서·절·행·열을 `map.json` 에 남긴다. 사본에서는 옮기면서 생기는 `paraFragment`·`sectionNoProse` 를 끄고, `sectionNoProse` 는 원래 문서를 검사한 결과에서 센다.

글은 쓴 쪽으로 나눈다. 공유 원본의 문자열(12자 이상)을 담은 글은 「모델」, 아니면 「코드」(제목·도입 문장·고정 문구)다. 「모델」 가운데 문서화 단계가 쓴 것(화면·테스트·BRD/PRD 내용)은 「모델(문서 단계)」로 따로 본다. 문서 작성 지시문이 바꿀 수 있는 글이 이것뿐이기 때문이다. 요구사항 문장은 그 앞 단계에서 쓴다.

지표는 셋이다. 지적 수, 1,000자당 지적 수, 30어절을 넘는 문장의 비율(문장은 마침표·물음표·느낌표로 끊는다). 읽기 쉬움 자체가 아니라 대리 지표다. 사람이 읽기 좋은지는 따로 봐야 한다.

## 3. 가설과 판정 기준

| 가설 | 채택 조건 | 기각 조건 |
|---|---|---|
| H-A/B. 범위 축소와 집계를 코드로 맞추면 같은 원본에서 정합성 위반이 없어진다 | (a)~(d) 가 모두 0 이고 기존 테스트가 모두 통과한다 | 어느 검사든 1건 이상 남거나, 기존 테스트가 깨진다 |
| H-R(코드). 코드가 쓰는 고정 글을 고치고 절마다 도입 문장을 넣으면 코드 글의 지적이 준다 | 코드 글의 1,000자당 지적이 0.97 → 0.485 이하(50% 이상 감소)이고 `sectionNoProse` 가 19 → 0 | 1,000자당 지적이 0.485 를 넘거나 `sectionNoProse` 가 1곳 이상 남는다 |
| H-R(모델). 문서 작성 지시문에 글쓰기 규칙을 넣으면 문서 단계가 쓰는 글의 지적이 준다 | 실제 Liner 로 문서 단계를 한 번 다시 돌린 결과에서, 모델(문서 단계) 글의 1,000자당 지적이 2.34 → 1.64 이하(30% 이상 감소)이고, 30어절 넘는 문장 비율이 1.0% → 0.73% 이하이고, 내용이 줄지 않는다 | 둘 중 하나라도 30% 에 못 미치거나, 아래 「내용」 조건을 어긴다 |

H-R(모델)의 「내용이 줄지 않는다」는 다음 셋으로 본다. 요구사항 수는 그대로다(문서 단계는 요구사항을 새로 쓰지 않는다). 범위 안 요구사항 가운데 테스트도 운영 확인도 없는 것이 기준선(0건)보다 늘지 않는다. 범위 안 요구사항 가운데 화면도 사유도 없는 것이 기준선(0건)보다 늘지 않는다.

H-R(모델)의 한계를 미리 적는다. 재실행은 한 번이고 모델 출력은 매번 달라서, 이 비교는 표본 1개짜리다. 다시 돌린 결과는 화면·테스트 수가 기준선과 다를 수 있다. 요구사항 문장의 긴 문장 65개는 이 재실행으로 바뀌지 않는다. 그것을 줄이려면 요구사항을 쓰는 단계의 지시문을 바꾸고 M1·M2 를 다시 재야 하므로 이번 범위에 넣지 않는다.

### H-N. 문장이 자연스러운가 (2026-11-24 추가, 3차 재실행 전에 적음)

사용자 요청으로 가설을 하나 더했다. hanlint 는 규칙으로 잡히는 것만 보므로, 한국어 문장이 자연스러운지는 다른 회사 모델(agy 의 Gemini 4 Hydrogen, `gemini-4-hydrogen-high`)이 같은 지시문으로 문서마다 1~5점을 매겨 본다. 리뷰는 메인 세션이 돌린다.

| | 화면설계서 | 테스트케이스 | BRD | PRD | 제안요약 | AGENTS | 평균 |
|---|---|---|---|---|---|---|---|
| 기준선(평가 묶음) | 4 | 3 | 2 | 2 | 2 | 2 | 2.5 |

채택 조건은 다시 돌린 문서의 평균이 3.5 이상(1점 이상 상승)이고 기준선보다 낮아진 문서가 없는 것이다. 평균이 3.5 에 못 미치거나 한 문서라도 낮아지면 기각한다. 같은 모델이 같은 지시문으로 매기더라도 점수가 실행마다 흔들릴 수 있고, 리뷰 한 번은 표본 1개다.

이 가설을 적은 때는 1차·2차 재실행을 이미 마친 뒤다. 지시가 엇갈려 도착했기 때문이다. 그래서 H-N 은 Hydrogen 과 hanlint 지침을 반영한 3차 재실행 결과로만 판정한다.

리뷰가 짚은 것과 반영한 곳은 다음과 같다.

- 같은 안내 문구의 반복(AGENTS.md 「가정값 기준 — …」 수십 번) → 「작업 순서」 머리에서 한 번 설명하고 테스트에는 `[가정값: REQ_11]` 같은 표시만 붙인다(코드).
- 영어 `Given/When/Then` → 「조건 / 동작 / 결과」로 적는다(코드). 조건을 결과에서 되풀이하는 것은 요구사항 문장 자체라서 지시문 규칙으로만 다룬다.
- 문체 혼용 → BRD 와 제안요약은 발주사가 읽으므로 합니다체, PRD·화면설계서·테스트케이스·AGENTS.md 는 개발자가 읽으므로 한다체로 코드 문구를 나눴다. 모델이 쓰는 글은 지시문에서 문서별로 문체를 정했다.
- 발주사용 문서의 내부 번호 → 번호만 든 괄호 「(DEC-02·09, TC-09)」는 문장에서 빼 문서 끝 「근거 번호」 표로 옮긴다(코드). 문장 성분으로 쓰인 번호는 뜻이 바뀔 수 있어 그대로 두고, 지시문에서 BRD 문장에 번호를 쓰지 말라고 했다.
- 어색한 고정 문구(「원본 ID 라」, 「사람이 읽는 같은 내용」, 「넘으면 큼 … 작음」)와 영문 뒤 조사 띄어쓰기를 고쳤다. 「PM에게 빈칸으로 돌려준다」는 디자이너 정의 파일의 문구를 모델이 따라 쓴 것이라 그 문구를 고쳤다.
- 글쓰기 규칙은 `app/writing_rules.py` 한 곳에 둔다. hanlint primer 의 「한국어 산문 일곱 줄」과 문장 규칙, Hydrogen 의 규칙 10개를 겹치지 않게 16줄로 줄였다. 두 지침이 부딪히는 긴 문장은 이렇게 정했다. 표 칸과 인수 조건은 짧게 쓰고, 서술 문단은 조건·이유·결과를 잇는 긴 문장을 가끔 써도 된다.

### 4-3. H-R(모델)을 두 번 돌린 경위

미리 정한 것은 재실행 한 번이었다. 그 한 번(1차)은 기각이다. 그래서 가설 판정은 「기각」으로 적고, 2차는 규칙을 고친 뒤의 추가 측정으로 따로 적는다.

| | 기준선 | 1차 | 2차 |
|---|---|---|---|
| 1,000자당 지적(문서 단계) | 2.34 | 3.91 | 1.36 |
| 30어절 넘는 문장 | 11/1,054 (1.0%) | 2/1,338 (0.1%) | 5/1,018 (0.5%) |
| `factListParagraph` | 16 | 100 | 9 |
| `endingRepeat` | 41 | 49 | 24 |
| `nounPile` | 20 | 3 | 8 |
| `outsideProfile` | 24 | 7 | 13 |
| 테스트 케이스 / 운영 확인 | 70 / 12 | 74 / (미집계) | 72 / 20 |
| 범위 안 요구사항 중 테스트 없음 / 화면·사유 없음 | 0 / 0 | (미집계) | 0 / 0 |

1차 규칙에는 「한 문장에 한 가지만 말한다」가 있었다. 모델은 문장을 잘게 끊었고, 긴 문장은 거의 사라졌지만 기대 결과 칸이 짧은 문장 서넛의 나열이 됐다. 그래서 `factListParagraph` 가 16 → 100 으로 늘었다. 2차에서는 그 문장을 빼고 「한 칸에 짧은 문장을 셋 이상 늘어놓지 않는다. 이어지는 내용은 두세 가지까지 잇는다」를 넣었다.

2차 수치는 기준을 넘지만 증거로는 약하다. 표본이 한 번이고, 1차 결과를 보고 규칙을 고친 뒤의 측정이기 때문이다. 같은 규칙으로 두세 번 더 돌려야 채택이라고 말할 수 있다.

1차는 완료된 프로젝트의 사본을 문서 단계로 되돌려 그대로 돌렸다. 범위 결정이 남아 있어서 디자이너가 처음부터 화면 5개만 그렸다. 2차는 문서 단계가 처음 시작하던 상태에 맞추려고 범위 결정과 소비자 의견을 지우고 시작했다. 두 번 모두 제품의 `Orchestrator.advance()` 경로를 썼고 원본 DB 는 건드리지 않았다.

Liner 비용은 잔액 55.431222 → 50.678399 달러, 합계 4.75달러다(1차 2.31, 2차 2.44). 상한은 10달러였다.

Hydrogen 리뷰와 hanlint 지침을 3절 H-N 에 적은 대로 반영한 뒤, 같은 방법으로 문서 단계를 한 번 더 돌렸다(3차, 범위 결정 없이 시작해 화면 8개 가운데 처음과 같은 5개를 고름).

|---|---|---|---|---|

3차도 1차·2차 결과와 리뷰를 보고 규칙을 고친 뒤의 측정이라 사후 조정이다. 1차 수치(3.91, 긴 문장 2/1,338)는 4-3절 표에 있다. H-R(모델)은 기각으로 정리한다. 최종 지시문으로 돌린 3차가 기준(30% 감소)에 못 미쳤기 때문이다. 2차가 넘긴 것은 그 실행 한 번의 결과였고, 서술 문단에 긴 문장을 허용한 최종 블록에서는 되풀이되지 않았다. 3차에서 걸린 규칙은 `endingRepeat` 24, `outsideProfile` 22, `nounPile` 17, `factListParagraph` 12 다. hanlint 수치와 읽는 사람의 인상이 같은 방향인지는 H-N 리뷰로 따로 본다.

코드 글의 지적은 0.19 에서 0.40 으로 다시 올랐다. 문서별 문체를 나누면서 한다체 도입 문장이 한다체 표 칸과 이어져 `endingRepeat` 가 문서마다 한 건씩 잡힌다. 고정한 입력에서는 기준(0.485 이하)을 지키지만 3차 입력에서는 0.52 다. 여유가 작다.

Liner 비용은 세 번을 합쳐 잔액 55.431222 → 48.313244 달러, 7.12달러다(1차 2.31, 2차 2.44, 3차 2.37). 상한 10달러 안이지만 한 번 더 돌릴 여유는 없다.

하지 못한 것도 적는다. BRD 의 표에서 ID 열(원문 ID, 가정 요구사항 ID, 열린 질문 ID)은 그대로 두었다. 문장 성분으로 쓰인 번호도 그대로다. 인수 조건의 「결과」가 「동작」을 되풀이하는 것과 요구사항 문장의 해요체는 요구사항 단계가 쓴 글이라 이번에 고치지 않았다. 묶음은 `after-code/`·`after-rerun/` 이 2차 시점(커밋 1b4d57e, 2차 원본), `after-code-v3/`·`after-rerun-v3/` 이 3차 시점이다. 3차를 만들면서 앞의 두 폴더를 11:44 부터 약 3분 동안 3차 내용으로 덮어썼다가 되돌렸다. 그 사이에 그 폴더를 읽은 평가는 다시 돌려야 한다.

## 5. 제출 v5 에 넣은 것과 뺀 것 (브랜치 `release/submission-v5`)

Hydrogen 자연스러움 점수(1~5, 같은 지시문, 메인 세션 측정)는 다음과 같다.
