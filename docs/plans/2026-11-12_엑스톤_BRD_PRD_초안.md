# BRD·PRD 초안 — PM·오너·디자이너 토론 결과 (2026-11-12)

- 방법: Fable 모델 하위 에이전트 3개(PM·오너·디자이너)가 같은 자료를 읽고 1라운드 안 작성 → 2라운드에서 쟁점 6개(D1~D6) 판정
- 읽은 자료: `CLAUDE.md`, `HANDOFF.md`, `docs/plans/2026-11-12_엑스톤_신청_주제와_구현범위.md`(신청서 정본), `docs/reports/2026-11-12_엑스톤_대회조사와_구축범위검토.md`(대회조사), `docs/reports/2026-11-12_엑스톤_개발문서_구조와_독자이해_조사.md`(문서조사)
- **상태: 초안.** 3절·4절의 「합의」는 세 역할이 같은 결론에 이른 것이고, 「쟁점」과 7절은 사용자가 정해야 한다. 수치 목표는 모두 제안값이다

## 0. 한 줄 정의

시키는 사람의 말을 질문으로 구체화해 **ID가 붙은 요구사항 원본** 하나로 만들고, 하는 사람과 시키는 사람이 **같은 기록**(결정·근거·변경·승인)을 보게 하는 에이전트. BRD·PRD·화면설계서·테스트 케이스는 그 원본의 **역할별 뷰**다.

## 1. 합의된 큰 방향 (세 역할 공통)

1. 신청서 기능 6개를 얕게 만들지 않고 **흐름 하나를 끝까지** 동작시킨다 — 근거: 심사 60%가 문제 정의·완성도, "실제 돌아가는 에이전트를 시연"(대회조사 1절)
2. 제품 가치의 중심은 **빠진 것 찾기**와 **바뀐 것 전달하기** — 근거: 실패 1~3위 빠진 요구 48%·소통 결함 41%·요구 변경 33%, 모호성 전반은 성공과 상관 미확인(문서조사 2절)
3. **단일 원본 + 역할별 뷰**. 4종 문서 이름은 뷰와 내보내기로 유지한다(신청서 약속) — 근거: 긴 생성 명세는 안 읽힘, 인수 조건 = 테스트 조건, 명칭·식별자 불일치가 실무 불만(문서조사 5절)
4. 시연 소재는 **소프트웨어 개발**(가상 꽃집 주 1회 정기구독 앱). 다른 업무로의 확장은 기획서 문장으로
5. 승인은 **요구사항 단위로 가볍게**, 변경 시 **영향받은 사람만** 재승인 — 근거: 착수 전 전원 사인오프는 안티패턴(문서조사 5절 10), 신청서 "필요한 담당자만"
6. Liner 검색 결과는 질문·기본값·누락 탐지의 **근거로 화면에 노출**하고 결정 로그의 근거 칸을 채운다

## 2. BRD 초안

### 사업 목표
- **문제**: 하는 사람(개발자)이 말 요청을 받고 되묻고, 검토하고, 바뀐 내용을 다시 확인하는 반복 작업
- **목표**: 그 반복을 요청 단계에서 끝낸다. 시키는 사람은 문서를 쓰지 않고 고르기만 한다
- **대회**: 11-27 결선 8팀 진출, 12-05 수상(총 900만 원, 결선 10분 시연 + 5분 질의응답 — 대회조사 1절)
- **대회 이후(오너 의견)**: 돈을 낼 쪽은 불편을 겪는 하는 사람 쪽(외주 개발사·프리랜서·사내 개발팀). 가격 기준점 ChatPRD Pro $15/월, BrainGrid $29/월부터(대회조사 4절)

### 문제의 크기
- 인용 가능: NaPiRE 10개국 228개 조직 — 빠진 요구 48%, 소통 결함 41%, 요구 변경 33%(문서조사 2절). 요구 변경이 테스터에게 안 전달되면 낡은 요구가 검증된다(Bjarnason, 같은 절)
- 인용 금지: 한국 통계, "수정 비용 100배" 같은 미확인 수치(문서조사 6절)
- 직접 잴 것: 사용자 본인 경험치(요청 1건당 되묻기 왕복, 검토 시간 — 회사 정보 없이 범위로), 시연 소재의 심은 결함 탐지 수, 말 요청에서 요청서까지 걸린 시간

### 대표 성공 지표 (D5 합의 — 2개)

| # | 지표 | 목표(제안) | 측정 |
|---|---|---|---|
| 1 | **누락 탐지** | 심은 결함 10개 중 8개 이상, 3회 반복 편차 기록 | 꽃집 요청 메모에 결함 10개(빠진 예외·완료 기준 없음·충돌)를 심고 정답표를 **구현 전에** 파일로 고정. 같은 입력을 한 번에 "PRD 써줘" 호출한 결과와 나란히 비교 |
| 2 | **변경 영향 재현율** | 90% 이상 | 가상 변경 20건(부담이면 최소 10건)의 정답 ID 목록을 미리 작성, 스크립트로 재현율·정밀도 계산. ID 링크로 결정적으로 계산하므로 실제로는 링크 생성 정확도를 재는 것임을 README에 밝힌다 |

- UX 시간 지표(첫 승인까지 시간 등)는 실제 사용자가 없어 대표 지표에서 뺀다. "작성자 1인 시연 1회 기록"이라고 밝히고 보조 수치로만 쓴다(직접 타이핑한 글자 수, 선택으로 답한 질문 수, 로그 타임스탬프)
- 제품 규칙으로 자동 검사: 첫 회 질문 8개 이하, 모든 질문에 "잘 모르겠어요", AI가 채운 값의 "가정" 표시 누락 0건
- 제출 조건: 새로 복제한 저장소에서 키만 바꿔 README대로 실행 성공(CLAUDE.md 규칙 2), 5분 영상에 업무 문제·실제 동작·Liner 지점 세 장면

## 3. PRD 초안

### 대상 사용자
- 시키는 사람: 원하는 결과는 있지만 조건으로 못 푸는 사람(사업가·기획자·현업)
- 하는 사람: 개발자·QA·디자이너, AI 코딩 에이전트

### 시나리오 (가상 꽃집 정기구독 앱)
- **S1 구체화**: 사장이 "매주 꽃 보내 주는 구독 앱, 일시정지도 되고 빨리 배송되게"를 붙여 넣는다 → 에이전트가 Liner로 구독 서비스 관행을 찾아 "배송 실패 시 ① 재배송 ② 환불 ③ 잘 모르겠어요"를 출처 2건과 함께 묻는다 → 6~8개 질문에 대부분 선택으로 답, "잘 모르겠어요"는 기본값 + 가정 표시 → 사장이 요약을 승인 → REQ-07 "일시정지: 다음 배송 48시간 전까지" 확정
- **S2 되묻기**: 개발자가 요청서에서 "결제일도 같이 미뤄지나요?"를 되묻기 → 사장에게 선택지 카드로 도착 → 답이 원본과 결정 로그(D-04)에 반영
- **S3 변경**: 사장이 "일시정지를 24시간 전으로" → 영향(요구사항 1·화면 1·테스트 2)과 전후 비교가 뜨고 개발자에게만 재승인 요청 → 결정 로그에 남음

### 기능 요구사항

| ID | 우선 | 요구 | 인수 조건(Given/When/Then) |
|---|---|---|---|
| FR-01 | P0 | 말·메모에서 요구 후보 추출, 출처 발화 연결 | Given 메모를 붙여 넣었을 때 When 분석하면 Then 각 후보에 원문 문장이 연결돼 보인다 |
| FR-02 | P0 | 질문 카드: 한 장씩, 선택지 2~4개 + "잘 모르겠어요", 첫 회 8개 이하, 남은 개수, 왜 묻는지 한 줄, 요청자 화면에 전문 용어 없음 | Given 완료 기준이 없는 후보가 있을 때 When 질문을 만들면 Then 선택지 2개 이상과 "잘 모르겠어요"가 있는 카드가 하나씩 나온다 |
| FR-03 | P0 | 근거가 필요하면 Liner 검색을 툴 콜링, 무엇을 왜 찾았는지와 출처 표시 | Given 관행·규정 근거가 필요한 질문일 때 When 카드를 보이면 Then 출처 URL이 1개 이상 붙는다 |
| FR-04 | P0 | 요구사항 원본: REQ-ID, Given/When/Then, 예외, 상태(확정/가정/미결정), 출처 발화, 결정 링크 | Given 사용자가 "잘 모르겠어요"를 골랐을 때 When 저장하면 Then 기본값이 들어가고 상태가 "가정"이다 |
| FR-05 | P0 | 역할별 뷰: 요청자 = 질문 카드·쉬운 요약 / 하는 사람 = 요청서 한 장(ID 표) / 4종 이름 뷰(BRD·PRD·화면설계서·TC) | Given 같은 REQ일 때 When 뷰를 바꾸면 Then ID와 내용이 같고 표현만 다르다 |
| FR-06 | P0 | 검증: 요구사항 간 충돌, 커버리지 빈칸(인수 조건·테스트 없는 요구사항, 예외 상태 없는 화면, 화면에 연결 안 된 요구사항) | Given 서로 어긋나는 두 요구사항이 있을 때 When 검증하면 Then 두 항목이 나란히 경고 배지와 함께 표시된다 |
| FR-07 | P0 | 요구사항 단위 승인과 결정 로그(누가·언제·왜·근거) | Given 요구사항이 승인됐을 때 When 기록을 열면 Then 누가·언제·왜·근거가 한 줄로 보인다 |
| FR-08 | P0 (11-22 컷 대상) | 변경 영향: ID 링크로 결정적 계산, 전후 비교, 영향받은 사람만 재승인, 낡은 항목 표시 | Given 확정본이 있을 때 When 변경을 입력하면 Then 영향받는 REQ·화면·TC ID와 전후 비교가 나오고 재승인 요청이 해당 역할에만 간다 |
| FR-09 | P0 좁게 (순서 쟁점) | 되묻기 1회 왕복: 하는 사람의 질문 1개 → 선택지 카드 → 답이 원본·로그에 반영. 질문 카드 부품 재사용, 스레드·알림·자유 대화 없음 | Given 개발자가 되묻기를 썼을 때 When 전송하면 Then 요청자 뷰에 선택지 카드로 뜨고 답이 원본에 반영된다 |
| FR-10 | 쟁점(P0 최소 / P1) | 요청서 한 장 뷰를 마크다운으로 내려받기(미정 항목 표시) | Given 승인된 원본일 때 When 내려받으면 Then 미결정·가정 항목이 표시된 마크다운 한 파일이 나온다 |
| FR-11 | P1~P2 | 기존 문서 업로드와 원본 대조 | Given 문서 파일을 올렸을 때 When 분석하면 Then FR-01과 같은 후보와 원본과의 불일치가 나온다 |

### 화면 (D4 합의: 한 앱 틀 + 역할 전환 + 영역 3개)
- 상단에 **현재 역할을 크게** 표시("지금: 시키는 사람 / 하는 사람"), 계정 없이 전환 버튼
- 왼쪽: 요청자 모드는 질문 카드, 하는 사람 모드는 요구사항 표(되묻기 버튼 포함)
- 가운데: 요구사항 원본(상태 배지·경고 배지)
- 오른쪽: 공유 기록 — **양쪽 모드에서 항상 보임**(결정 카드·변경 전후·영향·승인 대기)
- 화면 ID는 요구사항 ID(`REQ-`)와 겹치지 않게 `SCR-` 접두어를 쓴다
- 예외 상태: 빈 상태(예시 문장 3개) · 로딩("비슷한 서비스 관행을 찾는 중") · 검색 실패(출처 없이 계속, "근거 없음" 표시) · 미결정이 남으면 승인 대신 남은 질문으로 안내 · 하는 사람은 요청자 답을 고치지 못하고 이견만 남김

### "문서 간 정합성 검증"의 재정의 (D6 합의)
원본이 하나라 뷰끼리는 어긋날 수 없다. 검증은 **요구사항 간 충돌 · 연결 빈칸(커버리지) · 변경 후 낡은 항목**을 잡는다. 기획서에는 "불일치는 구조로 없애고, 검증은 누락·충돌·커버리지를 잡는다"로 쓰고, 영상에서는 "문서 간" 대신 "요구사항·화면·테스트 사이"로 풀어 말한다.

### Liner API 사용 (D1 합의)
- 본체 LLM: Liner Model API 경유, 모델 이름은 환경 변수 하나로 교체(liner-mark-1.3 또는 라우터 — 스모크 테스트로 기본값 결정). Liner 밖 모델은 테스트 전부 실패 시에만
- 검색: 질문의 선택지·기본값 근거, 업종별 흔한 예외 조건(누락 탐지 근거) — 결정 로그의 근거 칸
- 심사 문구가 "Liner Model**과** Liner Search"이므로 둘 다 쓴다(대회조사 1절)

### 하지 않는 것
2절 범위 밖 항목 + 준비도 점수, 다국어

### 0절 한 줄 정의에 더하는 것 — 핵심 고통의 재정의
- 핵심은 "빠진 것 찾기"보다 앞에 있다: **합의가 기록·명세로 남지 않아 완료를 검증할 수 없고, 그래서 작업이 끝나지 않는다**
- 되묻기(질문 카드·FR-09)는 기록을 **채우는** 수단, 변경 영향(FR-08)은 고정된 기록을 **바꾸는** 수단이다
- 시연 흐름(답 2): 완료 기준을 같이 정해 승인으로 고정 → 나중에 "아 이거 아닌데?" → 고정된 기록과 대조해 **원래 합의 위반인지, 새 변경 요청인지** 가른다 → 변경이면 영향과 "일정도 바뀌어야 한다"는 근거를 보인다

### 기술 스택 (사용자 결정)
