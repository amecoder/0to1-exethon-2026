## 0. 한 줄 결론 + 결정 요약

**결론**: 리서치의 합의 핵심 6개 중 0to1 에 실제로 비어 있는 것은 「실행 추적 내보내기」와 「MCP/A2A」 둘이다. 나머지는 있지만 구멍이 네 개 있다.

- 예상 못 한 오류가 나면 실행이 멈춘 채 못 빠져나온다
- 첨부 읽기 호출이 상한에 안 세어진다
- 흐름 파일 검사가 잘못 쓴 파일을 통과시킨다
- 도구 권한 한 줄을 빼면 G9 가 조용히 꺼진다

그래서 이번 라운드는 이 순서로 한다: **구멍 3건을 먼저 막는다 → 도구 관문을 등록부 하나로 닫는다 → 실행 추적을 OTLP 모양으로 내보낸다 → 안전장치 목록을 파일로 선언한다.**
프로젝트별 흐름 선택(b)은 **다시 미룬다.** 재현해 보니 화면·변경 요청·내려받기까지 함께 고쳐야 해서 11-23 까지 안전하게 끝낼 크기가 아니다(4절).

## 3. 결정별 명세

### X1. 예상 못 한 오류로 멈춘 실행을 실패로 바꾼다 (R1)

**결정**: 배경 작업이 어떤 예외로 죽든 그 프로젝트를 재시작 복구와 같은 길로 「실패」로 바꾼다. 발주사는 「다시 시도」를 누를 수 있다.
**이유**: 내구 실행은 합의 핵심(20/30)이고, 지금 구멍은 심사 중 한 번만 나와도 프로젝트가 잠긴다(완성도). 고치는 양이 작고 재시작 복구 코드(`recover_one`)를 그대로 쓴다.

| 항목 | 내용 |
|---|---|
| 가설 | 배경 작업이 잡지 않는 예외로 끝나도 프로젝트는 `running` 에 남지 않고, 다음 요청을 받는다 |
| 기준선 | 재현함: 단계 함수가 `KeyError` → pipeline `S2·running` 유지, 이후 요청 409 |
| 판정 | 같은 상황에서 상태 `failed`, 오류 문장에 「다시 시도」, `/retry` 가 202 이고 다음 확인 단계까지 가면 채택. 오류 문장·이벤트에 예외 메시지 본문이 들어가면 기각(내용 유출) |
| 측정 | 아래 테스트 3개 + 전체 pytest |

**구현**
1. `app/recovery.py`
   - 상수 `CRASHED = "예상하지 못한 오류로 작업이 멈췄어요. '다시 시도'를 누르면 이 단계를 처음부터 다시 합니다"`, `CRASHED_LANE = "예상하지 못한 오류로 처리가 멈췄어요. 같은 말을 다시 보내 주세요"`, `CRASHED_CONFIRM = "말씀을 처리하다 오류가 났어요. 다시 적어 주세요"`.
   - `recover_one(store, project_id, agents, team, liner, crash: str | None = None) -> bool`. `crash` 는 예외 **종류 이름**(`type(exc).__name__`)만 받는다. `crash` 가 있으면 `restore_confirmation(error=CRASHED_CONFIRM, crash=crash)` / `mark_interrupted(error=CRASHED, crash=crash)` / `ChangeDesk.mark_interrupted(error=CRASHED_LANE)` 로 부른다. 없으면 지금과 같다.
2. `app/orchestrator.py`: `mark_interrupted(self, error: str = INTERRUPTED, crash: str | None = None)`, `restore_confirmation(self, error: str | None = None, crash: str | None = None)`. 이벤트는 지금의 `run_interrupted` 를 그대로 쓰고 `crash` 가 있을 때만 `data["crash"] = crash` 를 더한다(새 이벤트 종류를 만들지 않는다 — 화면 라벨 `frontend/src/lib/labels.ts:54` 가 이미 있다).
3. `app/change_desk.py`: `mark_interrupted(self, error: str = INTERRUPTED)`.
4. `app/routes_pipeline.py` `run_then_release`:
   ```python
   try:
       for fn in work:
           fn()
   except Exception as exc:  # any crash: the project must not stay `running` until a restart
       log.exception("프로젝트 %s 의 배경 작업이 멈췄습니다", project_id)
       try:
           recover_one(store, project_id, agents, team, liner, crash=type(exc).__name__)
       except Exception:
           log.exception("프로젝트 %s 를 실패로 바꾸지 못했습니다", project_id)
   finally:
       store.release_run(project_id, token)
   ```
   `recover_one` 은 저장소에서 새로 읽으므로 죽은 작업의 낡은 revision 과 부딪치지 않는다. 잠금은 아직 이 작업이 쥐고 있다.

**테스트** (`tests/test_recovery.py`)
- `test_a_crashed_stage_becomes_failed_and_can_be_retried`: API 로 프로젝트를 만들고 `app.orchestrator.RUNS` 의 `problem` 을 `KeyError("비밀문장")` 을 내는 함수로 바꾼 뒤 `/input` → 프로젝트 조회에서 `pipeline.status == "failed"`, `stage == "S2"`, `error` 에 「다시 시도」, `run_interrupted` 이벤트의 `data.crash == "KeyError"`, 응답 전체에 「비밀문장」 없음. `RUNS` 를 되돌리고 `/retry` → 202, `CP1`·`awaiting_confirmation`.
- `test_a_crash_at_a_confirmation_returns_to_the_confirmation`: CP1 에서 `app.orchestrator.classify` 가 `KeyError` 를 내게 하고 사유를 적어 반려 → `CP1`·`awaiting_confirmation`, `error == CRASHED_CONFIRM`.
- `test_a_crashed_change_mapping_fails_the_item`: 완료된 프로젝트에서 `ChangeDesk.map_change` 가 `RuntimeError` 를 내게 하고 `/changes` → 그 변경 항목 `status == "failed"`, `error == CRASHED_LANE`, 다음 `/changes` 요청이 409 가 아님.

**완료 조건**: 세 테스트 통과, 기존 726개 무수정 통과.

### X3. 흐름 파일 검사 구멍 막기 (R3, R9 는 제외)

**결정**: 읽는 시점에 아래를 `FlowError` 로 막는다.
**이유**: 「잘못된 흐름은 시작 전에 막힌다」(H11·H14)가 확장성 주장의 한 축인데 12가지가 샌다. 특히 오타 난 키는 판 고정이 빠지는 조용한 실패다.

| 항목 | 내용 |
|---|---|
| 가설 | 아래 9종의 잘못된 흐름 파일은 읽을 때 무엇이 잘못인지 적힌 `FlowError` 로 막힌다 |
| 기준선 | 재현함: 9종 모두 받아들여짐 |
| 판정 | 9종 모두 `FlowError` + 기본 흐름·`LITE`·`RENAMED`(tests/test_flow.py)가 그대로 통과하면 채택 |

**구현** (`app/flow.py`, `app/runs.py`)
1. 허용 키: 파일 최상위 `{"id", "title", "stages"}`, 단계 `{"id", "kind", "title", "agents", "rework", "run", "on_approve", "features"}`. 그 밖의 키 → `FlowError(f"{단계 id}: 모르는 키 「{key}」 (쓸 수 있는 키: …)")`. 최상위는 `f"{path}: 모르는 키 「{key}」"`.
2. id: 글자열이어야 하고 `^[A-Za-z0-9_-]{1,20}$` 에 맞아야 한다 → 아니면 `FlowError(f"{n}번째 단계의 id 「{id}」 는 영문·숫자·-·_ 20자 이내여야 해요")`. (지금의 `str(item["id"])` 변환을 없앤다.)
3. `run` 은 work 에만, `rework` 는 confirm 에만 → `FlowError(f"{s.id}: run 은 work 단계에만 적어요")` / `…rework 는 confirm 단계에만 적어요`.
4. 같은 일은 한 흐름에 한 번: 둘째 단계에서 `FlowError(f"{s.id}: 일 「{s.run}」 은 이미 {first.id} 가 돌려요 (한 흐름에 한 번)")`.
5. 같은 기능은 한 확인 단계에만: `FlowError(f"{s.id}: 기능 「{name}」 은 이미 {first.id} 에 있어요")`.
6. 일의 선행 조건. `app/runs.py` 에 `REQUIRES: Mapping[str, tuple[str, ...]] = {"requirements": ("problem",), "finalize": ("requirements",), "documents": ("finalize",), "prototype": ("documents",)}` 를 두고, work 단계마다 그 앞 단계들의 `run` 에 선행 일이 없으면 `FlowError(f"{s.id}: 「{s.run}」 앞에는 「{need}」 단계가 있어야 해요")`. `load_flow` 가 `RUNS` 와 함께 읽어 `_check` 에 넘긴다.

### E1. 도구 관문 닫기 — 등록부 하나가 Liner 호출 전부를 정한다

**결정**: `app/tools.py` 를 「Liner 로 나가는 호출 전부의 목록」으로 만든다. 에이전트가 선언하는 도구 6종(지금 그대로)과 선언 없이 쓰는 내장 호출 3종(모델·음성·첨부)을 함께 적고, G7 이 세는 이벤트 목록을 이 등록부에서 만든다. 실행기 밖에서 Liner 를 부르지 못하게 테스트로 묶는다. 모델 호출을 도구 권한으로 막지는 않는다(모델 없는 에이전트는 뜻이 없다 — 리서치의 「tool mediation」도 도구가 대상이다).

### E2. 실행 추적 내보내기 — 이벤트 기록을 OTLP/JSON span 으로

**결정**: 이벤트 스키마를 바꾸지 않고, 기존 기록에서 span 을 **계산**해 내보내는 읽기 전용 주소를 하나 둔다. 본문(지시문·질의·모델 출력·검색 결과)은 내보내지 않고 누가·무엇을·얼마나·얼마에만 낸다.
**이유**: 트레이싱은 런타임 14개 중 빠진 곳이 0개이고 OpenTelemetry 로 모이고 있다(리서치 3절 6번). 0to1 은 재료(호출마다 모델·토큰·비용·시간)를 이미 갖고 있어 값이 싸다. 실행 경로를 건드리지 않아 제출본에 넣어도 안전하다. 「다른 관측 도구로 가져갈 수 있다」가 확장성의 구체적 근거가 된다.

| 항목 | 내용 |
|---|---|
| 가설 | 기존 이벤트 기록만으로 「Liner 호출 1건 = span 1개, 부모는 그 호출이 일어난 단계」인 추적을 만들 수 있다 |
| 기준선 | 주소 없음(404), span 0개 |
| 판정 | 꽃집 예제 전체 실행(가짜 Liner)에서 호출 span 수 == `calls_used(events)`, 모든 `parentSpanId` 가 같은 추적 안의 span 을 가리킴, 원문 문장·지시문·출력이 한 글자도 안 나감 → 채택. 하나라도 어긋나면 기각 |
| 한계(미리 적음) | OTLP/JSON **모양**까지만 검증한다. 실제 수집기(Collector·Jaeger)에 넣어 보지 않는다(새 외부 서비스 금지). 문서·기획서에는 「OTLP/JSON 형식으로 내보냄, 수집기 연동은 미검증」이라고 쓴다. 속성 이름은 OTel GenAI 의미 규약(아직 개발 단계 규약)에서 가져왔다 |

**구현** — 새 파일 `app/trace.py` (순수 함수, 150줄 이내)
```python
def otlp_trace(project_id: str, name: str, events: Sequence[Mapping[str, Any]]) -> dict[str, Any]: ...
```
- 모양: `{"resourceSpans": [{"resource": {"attributes": [service.name="0to1", zerotoone.project.id, zerotoone.project.name]}, "scopeSpans": [{"scope": {"name": "0to1.events"}, "spans": [...]}]}]}`
- id: `traceId = sha256(project_id).hexdigest()[:32]`, `spanId = sha256(f"{project_id}:{key}").hexdigest()[:16]` — key 는 뿌리 `"root"`, 단계 span `"stage:{시작 이벤트 seq}"`, 호출 span `"call:{seq}"`. 같은 기록이면 언제나 같은 결과다.
- 시간: `startTimeUnixNano`·`endTimeUnixNano` 는 **글자열**(OTLP/JSON 의 64비트 정수 표기). 이벤트 `ts`(UTC ISO)를 나노초로.
- span 3종
  1. 뿌리 1개: 이름 `project`, 첫 이벤트~마지막 이벤트. 이벤트가 없으면 `spans` 는 빈 목록.
  2. 단계 span: `stage_started` 마다 1개(재작업이면 같은 단계가 여러 개). 끝은 그 뒤 같은 단계의 첫 `stage_completed`, 없으면 다음 `stage_started` 직전 이벤트(또는 마지막 이벤트)의 시각. 이름 `stage {id}`, 속성 `zerotoone.stage.id`, `zerotoone.stage.agents`(쉼표로 이은 글자열, 있을 때만). 부모는 뿌리. 완료 없이 끝났으면 `status.code = 2`.
  3. 호출 span: 종류가 `CALL_EVENTS` 에 있는 이벤트마다 1개. 끝 = 이벤트 `ts`, 시작 = 끝 − `duration_ms`(없으면 0). 부모 = 그 이벤트 시점에 열려 있는(시작했고 아직 안 끝난) 단계 span 중 `stage` 가 이벤트의 `stage` 와 같은 것, 없으면 뿌리. `kind = 3`(CLIENT).
     - 이름: `liner_chat`·`liner_attachment` → `chat {model}`, 나머지 → `execute_tool {call_of(type, api)}`
     - 속성(값이 None 이면 넣지 않는다): `gen_ai.operation.name`(`chat`/`execute_tool`), `gen_ai.provider.name="liner"`, `gen_ai.agent.id`(actor), `gen_ai.request.model`(data.model), `gen_ai.response.model`(data.answered_model), `gen_ai.usage.input_tokens`(prompt_tokens), `gen_ai.usage.output_tokens`(completion_tokens), `gen_ai.tool.name`(등록부 id), `zerotoone.cost_usd`(cost), `zerotoone.schema`(schema), `zerotoone.routing_strategy`, `zerotoone.budget_mode`, `zerotoone.result_count`, `zerotoone.seq`
     - `data.error` 가 있으면 `status = {"code": 2, "message": "error"}` (오류 문장 본문은 넣지 않는다)
- span 이벤트(각 span 의 `events` 목록, `{"timeUnixNano", "name", "attributes"}`): `guardrail` → 이름 `guardrail.{id}`, 속성 `outcome`·`tool`·`limit`(있을 때). `confirmation` → 이름 `human.confirmation`, 속성 `cp`·`approved`·`version`. `run_interrupted`·`run_retried` → 같은 이름. 붙이는 곳은 그 시점에 열려 있는 단계 span, 없으면 뿌리. **`detail`·`reason`·`who` 는 넣지 않는다.**
- 속성 값 표기: `{"key": k, "value": {"stringValue"|"intValue"(글자열)|"doubleValue"|"boolValue": v}}`.
- 내보내지 않는 것(테스트로 지킴): `task`, `output`, `query`, `results`, `answer`, `prompt`, `detail`, `reason`, `content`, 파일 이름.

주소: `app/routes_delivery.py` 의 프로젝트 라우터에 `GET /api/projects/{project_id}/trace` → `otlp_trace(id, name, source["events"])`. 없는 프로젝트 404. 시연 모드 프로젝트도 같은 함수로 된다(이벤트가 있으면). 결과물 zip 에는 넣지 않는다.

**테스트** (`tests/test_trace.py`)

### E3. 안전장치 목록 파일 + 시작 때 검사 (R4·X4 포함)

**결정**: G1~G9 의 「어디에 걸리는지 · 규칙인지 모델인지 · 판정을 못 하면 어떻게 되는지 · 어떤 에이전트의 어떤 도구가 필요한지」를 `policies/guardrails.json` 에 선언하고, 서버가 뜰 때 읽어 검사한다. **문턱값·켜고 끄기는 옮기지 않는다**(지금처럼 환경 변수) — G1~G9 호출 지점을 건드리지 않는다는 D6 의 이유가 그대로 유효하다. 이름은 「정책 엔진」이 아니라 「안전장치 목록」이다.
**이유**: 리서치 체크리스트 2번(「결정적 규칙이 무엇인가」)에 답하는 자료가 코드에 흩어져 있고, 에이전트 파일의 `guardrails` 칸은 아무도 읽지 않으며 G9 는 목록에 없다. 무엇보다 R4: 도구 권한 한 줄로 G9 가 조용히 꺼진다. 목록에 「G9 는 coordinator 의 liner_decisions 가 필요」를 적고 시작 때 막으면 구멍이 닫힌다. 코드와 목록이 어긋나면 테스트가 실패하게 해서 슬라이드용 문서가 되지 않게 한다.

## 4. 미루거나 버린 것과 이유

- **(b) 프로젝트별 흐름 선택 + 단계 번호 빼기 — 미룸.** 이번에 재현해서 범위를 다시 쟀다. 흐름을 프로젝트에 묶으면 함께 고쳐야 하는 것: `views.py:30`(KeyError), `checks.py:162-166`(승인 검사가 0건이 됨), `recovery.py:47`, `ConfirmBody.cp`, 변경 요청 레인(`change_desk.py:40-42, 271` — 문서 단계가 없는 흐름에서 변경을 승인하면 없는 단계 `S5` 로 보내 R1 로 죽는다), 내려받기(`export.py:51-65` — CP4 승인과 화면이 있어야 준비됨이라 짧은 흐름은 「완료」인데 받을 것이 없다), 고객 의견 수집의 `"CP3"`·`"CP4"`(`stage_documents.py:134`, `stage_development.py:72`), 단계별 예상 비용 표(`limits.py:30`), 다른 프로젝트의 CP2·CP4 를 보는 회사 기억(`store.py:261, 281`), 그리고 화면의 진행 막대·확인 카드(48곳). 화면의 48곳은 대부분 「요구사항 업무의 화면」 그 자체라 옮길 곳이 없다. 반만 하면 미완성 기능이 제품에 들어간다. 마감 뒤 순서: 흐름 id 를 프로젝트에 저장 → 확인 단계 검사를 흐름 파일 선언으로 → 레인·내려받기를 흐름의 역할로 → 화면이 단계 목록을 서버에서 받기.
- **MCP/A2A 노출 — 미룸.** 합의 핵심이지만 새 외부 표면과 의존성(MCP SDK)이다. 대회 규칙은 이미 API 로 충족한다. 로드맵 3번으로 올린다(5절).
- **에이전트 신원·인증, 회사별 격리 — 미룸.** 플랫폼급 항목이고 SDK 급 제품에는 없는 것이 보통이다(리서치 3절). 4일 안에 인증을 넣으면 시연 경로 전체가 흔들린다.
- **스케줄러·큐 — 안 함.** 30개 중 9개만 다루고, 0to1 에 동시 실행 요구가 없다. 프로젝트당 작성자 1명 잠금으로 충분하다.
- **검색되는 장기 기억(벡터) — 안 함.** 범위 밖(그래프·벡터 DB 금지). 회사 자료 + Rerank 로 효과가 이미 측정됐다.
- **호출 단위 재개(체크포인트) — 미룸.** 단계 함수 5개를 다시 써야 하고 가짜 Liner 로는 회귀를 못 본다. X1 로 「멈춘 채 갇힘」만 없앤다.
- **도구 호출마다 사람 승인 콜백 — 안 함.** 되돌릴 수 없는 도구가 없다. 결과물을 밖으로 내보내는 것(GitHub)은 사람이 버튼으로 직접 한다.
- **안전장치 문턱값·켜고 끄기를 파일로 — 미룸.** G1~G9 호출 지점을 모두 건드린다(D6 의 이유 그대로). E3 은 목록과 검사까지만.
- **비용 예산 추가 기능(토큰 예산, 요구 입력 전 비용 포함 R11) — 미룸.** 호출·시간·금액 상한과 예산 모드가 이미 있고 X2 로 구멍을 막는다. R11 은 첫 잔액 기록 시점을 옮겨야 해서 `spent_usd` 를 쓰는 테스트 다수에 닿는다.
- **이벤트에 `tool` 칸 추가 — 안 함.** 이벤트 모양이 바뀌면 시연 기록(replay)·기존 단언에 닿는다. E2 는 `call_of()` 로 계산한다.

- **R8·R9·R10 — 적어만 둔다.** 기본 흐름·기본 팀에서는 드러나지 않는다. (b) 를 할 때 함께 고친다(R9: 같은 확인 단계의 `snapshot` 뒤 `bind_version` 금지, R10: 일마다 필요한 쓰기 권한을 시작 때 검사).
