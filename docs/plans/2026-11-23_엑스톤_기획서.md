# 0to1(영일) 기획서

## 1. 문제 (누가 · 어떤 문제 · 얼마나 불편)

실제 소프트웨어 개발 프로젝트를 수행하면서 PM이나 기획자가 부재하거나, 담당자의 요구사항 분석 역량이 부족해 요구사항이 충분히 구체화되지 않은 상태에서 개발이 시작되는 경우를 자주 경험했습니다.

예를 들어, 꽃집을 운영하는 소상공인이 서비스 개발을 의뢰하면서 구두나 메신저를 통해 요구사항을 전달하지만, 기획자와 개발자가 제작한 결과물을 확인한 뒤 자신의 의도와 다르다는 의견을 전달하는 경우가 있습니다. 요구사항이 명확한 명세로 기록되어 있지 않으면 최초에 합의한 내용을 확인하기 어렵고, 반복적인 수정 작업으로 인해 프로젝트의 완료 시점도 불명확해집니다.

또한 담당자마다 문서에 대한 이해도와 작성 역량이 달라 산출물의 품질에도 편차가 발생합니다. 요구사항이 불명확하거나 문서 간 내용이 일치하지 않고, 예외 조건이나 완료 기준이 누락되는 경우가 대표적입니다. 이로 인해 개발자는 반복적으로 문서를 검토하고 피드백해야 하며, 요구사항이 변경될 때마다 기획자와 개발자가 관련 문서를 다시 확인하고 누락되거나 충돌하는 내용을 찾아 수정하는 데 많은 시간과 노력을 소비하고 있습니다.

이러한 문제는 개인의 업무 경험에 국한되지 않습니다. 전 세계 10개국 228개 조직을 대상으로 진행한 NaPiRE(국제 요구공학 실태조사, arXiv:1611.10288) 연구에 따르면, 다음과 같은 문제가 소프트웨어 개발 과정에서 주요 문제로 지목되었습니다.

- 불완전하거나 누락된 요구사항: 48%
- 프로젝트 수행팀과 고객 간 의사소통 문제: 41%
- 지속적인 목표 및 요구사항 변경: 33%
- 추상적이고 불명확한 요구사항: 33%
- 프로젝트 수행팀 내부의 의사소통 문제: 27%

이러한 문제는 AI 코딩 에이전트를 활용하는 개발 환경에서도 발생할 수 있습니다. AI가 코드를 빠르게 작성하더라도 불완전하거나 모호한 명세를 기반으로 개발할 경우, 요청자의 의도와 다른 기능이 구현되어 반복적인 수정과 검증이 필요하기 때문입니다.

따라서 소프트웨어 개발의 생산성과 품질을 높이기 위해서는 단순히 개발 속도를 높이는 것뿐만 아니라, 개발 초기 단계부터 요구사항을 명확하게 정의하고 문서 간 정합성을 검증하며, 이해관계자 간 합의를 체계적으로 관리할 수 있는 환경이 필요합니다.

## 2. 해결 방식

**0to1(영일)**은 구두로 전달된 요구사항을 이해관계자가 확인하고 합의한 최초의 개발 명세로 구체화하는 AI 멀티 에이전트 서비스로, 라이너 .EXE-THON 2026 출품작입니다. 발주사(요청자)가 메신저 대화, 메모, 회의 녹음, 이미지, PDF 등 다양한 형태로 요구사항을 전달하면 이를 원본 자료로 저장하고, AI 에이전트들이 협업하여 요구사항을 분석하고 구체화합니다.

조율자, FDE 리드(고객의 문제와 개발 범위를 정의하는 현장 중심 엔지니어), 리서처, PM, 디자이너, 개발자, QA 등 7개의 전문 에이전트와 소비자 에이전트가 참여하며, 사전에 정의된 팀 관계도에 따라 지정된 연결 내에서만 소통하고 협업합니다.

에이전트들은 요구사항의 불명확한 부분과 누락된 내용을 식별하고, 이를 질문 카드 형태로 구성하여 발주사에게 확인을 요청합니다. 모든 질문에는 ‘잘 모르겠어요’라는 선택지를 제공하여 발주사가 전문적인 지식이 없더라도 부담 없이 답변할 수 있도록 합니다. 또한 에이전트들이 협의를 통해 도출한 기본값을 별도로 제시하고, 발주사는 자신의 의도와 다른 항목만 수정할 수 있도록 합니다.

발주사는 기본 4회의 확인 절차와 변경 발생 시마다 1회의 추가 확인을 통해 요구사항을 확정합니다. 에이전트들은 이를 바탕으로 다음과 같은 산출물을 생성합니다.

- BRD(사업 요구사항 정의서)
- PRD(제품 요구사항 정의서)
- 화면설계서
- 테스트 케이스
- 프로토타입

프로토타입은 앱의 경우 모바일 기기별로, 웹의 경우 데스크톱부터 모바일까지 다양한 화면 환경에서 확인할 수 있도록 합니다.

확정된 요구사항과 이해관계자의 확인 이력은 기록으로 관리합니다. 요구사항이 변경되면 프로그램 코드가 변경 영향 범위를 산출하고, PM 에이전트가 이를 바탕으로 판단합니다. 이후 결과물에 대한 이의가 제기되면 기존 합의 기록과 대조하여 ‘기존 합의사항 위반’인지 ‘새로운 변경 요청’인지 구분합니다.

AI 에이전트의 판단 확신도가 낮은 경우에는 사람에게 판단을 위임하며, 최종 의사결정 권한은 프로그램 코드 수준에서 통제합니다. 또한 유해한 목적의 요청은 작업 시작 전에 차단하고, 에이전트 호출 횟수, 실행 시간, 비용이 사전에 설정된 상한을 초과하면 작업을 중단하고 사람의 확인을 요청합니다.

최종 산출물은 압축 파일 형태로 제공하며, 요구사항 및 설계 관련 문서 4종과 프로토타입, AI 코딩 도구가 활용할 수 있는 `AGENTS.md`, 결재권자의 의사결정을 지원하는 `제안요약.md`를 포함합니다. 본 서비스의 시연은 가상의 꽃집 ‘꽃님’을 대상으로 진행하며, 시연에 사용되는 모든 예제, 녹화 자료 및 평가 데이터는 직접 제작한 가상 데이터입니다.

## 3. Liner API 활용

Liner API(프로그램 사이의 기능 호출 접점)는 요구 구체화부터 검증까지 사용합니다. 모든 호출의 담당·작업·시간을 기록하고 모델 호출은 비용도 남깁니다.

| 어디서 | Liner API | 하는 일 |
|---|---|---|
| 모든 에이전트 발화 | Router/Model API | 질문 카드·요구사항·문서 4종·프로토타입 생성과 변경 영향 매핑. 답한 모델을 활동 기록에 표시 |
| 리서처의 도구 호출 | Search Agent API, 실패 시 Search API | 발주사 분야의 근거 검색, 출처 문단을 근거로 저장 |
| 사실 확인 | Decisions API | 인용문 대조를 통과한 문장이 그 근거로 뒷받침되는지 판정 |
| 용도 검사 | Decisions API | 해로운 목적은 저장 전에 막고 단어만 겹치는 정상 요청은 통과 |
| 「아 이거 아닌데?」 | Decisions API | 확정 기록과 불만을 대조해 합의 위반인지 새 변경 요청인지 판정 확률을 받음 |
| 변경 요청 연결 | Rerank API | 가까운 요구사항 상위 5개와 점수를 PM에게 전달 |
| 흐름도·상품 사진 | Visualization API, Images API | 화면 순서를 흐름도로, 개발자가 고른 자리(최대 3장)에 사진 생성 |
| 회의 녹음 | Audio transcriptions API | 녹음을 글로 받아 원문으로 저장 |

비용 상한(호출 수·시간·비용)은 Credits API(무료)로 단계마다 잔액을 기록해 판정합니다.

## 4. 성과

소표본 측정이며 실제 고객 성과는 아닙니다. 가상 꽃집 데이터로 2026-11-16에 liner-claude-router를 사용해 각 3회 반복했습니다. 용도 검사와 잡담 거르기는 2026-11-18 측정입니다. 가짜 응답 실행은 지표에서 제외했습니다.

| 평가 | 대상 | 결과 | 목표 |
|---|---|---|---|
| 심은 결함 탐지 | 요청 메모에 심은 결함 10개 중 찾은 수 | 9 · 10 · 9 / 10 | 8 이상 |
| 변경 영향 재현율 | 변경 20건 | 1.000 · 1.000 · 1.000 | 0.9 이상 |
| 불만 판정 정확도 | 불만 20건 | 1.00 · 1.00 · 1.00 | 0.9 이상 |
| 용도 검사(2회) | 해로운 요청 12건, 정상 요청 16건 | 막음 12 · 12 / 12, 잘못 막음 0 · 0 / 16 | 막음 11 이상, 잘못 막음 1 이하 |
| 잡담 거르기 | 잡담 변경 10건, 잡담 불만 6건, 진짜 불만 20건 | 관련 없음 10/10, 무관 6/6, 진짜 불만을 버림 0/20 | 9 이상, 5 이상, 1 이하 |

실제 Liner로 정상 흐름을 끝까지 돌린 시연은 두 번 기록했습니다. 첫 녹화는 팀이 일한 시간 약 19분에 호출 24번, 비용 $3.63이었습니다. 마지막 녹화는 약 24분에 호출 27번, 비용 $5.31이었습니다. 마지막 녹화의 비용에는 중간에 한 단계가 실패해 다시 시도한 몫이 들어 있습니다. 다만 확신도 문턱 0.6과 비용·호출 상한은 아직 제안값입니다.

## 5. 확장 가능성

외주 개발사·사내 개발팀의 기획자·개발자와 일을 맡기는 쪽이 사용 대상입니다. 확정 기록을 AGENTS.md로 넘겨 요구사항을 코딩 에이전트의 입력으로 연결합니다.

업무 단계와 팀 역할·권한은 파일로 정의하고 유료 호출·허용 도구는 등록부에서 관리합니다. 안전장치와 사람 확인은 시스템 규칙으로 강제합니다. 다만 새 업무에는 단계별 지시문·출력 형식·검증 코드·업무 화면도 필요합니다. 요구사항까지만 도는 별도 흐름은 가짜 응답으로 실행 구조를 확인했으며 화면에서 선택하는 기능은 없습니다.

다음 단계는 다른 에이전트가 0to1을 부르는 것입니다. 제출본 밖의 개선 브랜치에서 MCP(에이전트가 도구를 부르는 공개 규격)·A2A(에이전트끼리 일을 맡기는 공개 규격) 연결과 토큰 신원·회사별 자료 분리를 구현해 시험하고 있습니다.

## 6. 기존 결과물과 새로 만든 부분

기존 결과물은 없으며 코드·프롬프트·문서는 전부 대회 기간(2026-11-12 ~)에 새로 만들었고, FastAPI·React 등 공개 소프트웨어 의존성은 버전을 고정해 사용합니다.
