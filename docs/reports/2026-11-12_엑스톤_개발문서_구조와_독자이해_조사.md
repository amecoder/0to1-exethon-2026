|---|---|---|

### 요구사항 문장 형식

- **사용자 스토리**: "As a… I want to… So that…" (Connextra, 2001) [요약] https://www.agilealliance.org/glossary/user-story-template/ · **INVEST**: Independent·Negotiable·Valuable·Estimable·Small·Testable [요약] https://xp123.com/invest-in-good-stories-and-smart-tasks/ (2003)
- **인수 조건**: 이해관계자가 수용하려면 충족해야 하는 조건이며 **테스트 조건으로 볼 수 있다**. 시나리오형(Given/When/Then)과 규칙형(체크리스트·입출력 표) [원문] ISTQB CTFL v4.0.1 §4.5.2 https://istqb.org/wp-content/uploads/2024/11/ISTQB_CTFL_Syllabus_v4.0.1.pdf (2024-09-15)
- **Gherkin**: Given(초기 맥락) / When(사건) / Then(기대 결과), Rule = 비즈니스 규칙 하나, Example = 그 규칙의 예 [요약] https://cucumber.io/docs/gherkin/reference/
- **EARS** 5패턴 [요약] https://alistairmavin.com/ears/
  - 상시 "The <system> shall …" · 상태 "While <조건>, …" · 이벤트 "When <트리거>, …" · 선택 기능 "Where <기능>, …" · 원치 않는 동작 "If <트리거>, then …"
- **ISO/IEC/IEEE 29148:2018** 품질 특성 (표준 본문은 유료, 2차 문헌으로 확인) [원문—2차] https://annals-csis.org/proceedings/2023/pliks/9537.pdf (2023)
  - 개별 요구사항: necessary · appropriate · unambiguous · complete · singular · feasible · verifiable · correct · conforming
  - 요구사항 집합: complete · consistent · feasible · comprehensible · able to be validated
  - 2018판은 2024년 재확인, DIS 29148로 대체 예정 [원문] https://www.iso.org/standard/72089.html
- **Definition of Done**: 충족 못 한 항목은 릴리스도 리뷰 제시도 못 한다 [요약] https://scrumguides.org/scrum-guide.html (2020-11)

### 화면설계서 (한국 실무)

- 같은 문서의 다른 이름: 화면설계서·화면정의서·화면명세서·스토리보드(SB) [요약] https://treesoop.com/blog/screen-design-document-writing-guide-2026 (2026-08-27)
- 필수 8항목(같은 글): 화면 ID · 경로·진입 조건 · 레이아웃 · 입력 항목 정의 · 버튼·링크 동작 · 권한별 노출 차이 · 오류·예외 처리와 메시지 · 데이터 출처. ID 예: 업무 영역 3자 + 일련번호, 팝업 `MEM-003-P01`
- 문서 구성: 표지 · 작업 히스토리(버전·반영 페이지·날짜·수정자) · 목차 · 개요 · IA · 화면 ID 목록 · 플로우 · 정책. **쪽수가 아니라 화면 ID로 참조** [요약] https://www.elancer.co.kr/blog/detail/66 (2022-11-29), https://yozm.wishket.com/magazine/detail/1112/ (2021-10-26)
- 한 장 구성: 상단 화면명, 좌측 흑백 와이어프레임 + 번호, 우측 디스크립션(요소명·설명·기능과 결과·특이사항) [요약] https://brunch.co.kr/@kiwon4321/29 (2023-11-25), [원문] https://m.blog.naver.com/gpdls6875/223440664070 (2024-05-08, 개인 블로그)
- 삭제된 화면은 지우지 않고 취소선과 비고로 남김, 유효성 검사는 [상황·문구·처리] 표로 분리 [요약] https://velog.io/@corone_hi/화면-설계서-작성-방법 (2024-08-07)
- 공공 표준(CBD SW개발 표준 산출물 관리 가이드, 2011): 화면 산출물 이름은 "사용자 인터페이스 설계서", 요구사항 추적표는 분석 단계, 단위시험 케이스·통합시험 시나리오는 설계 단계 [요약—해설 블로그] https://blog.acronym.co.kr/712 (2024-11-26)
- 해외 대응물: 와이어프레임 주석(번호 콜아웃, 조건부 요소·엣지·에러 케이스, 확정/임시 문구 구분) [요약] https://balsamiq.com/learn/articles/wireframe-annotations/ (2025-05-09), Figma Dev Mode 주석(Development·Interaction·Accessibility·Content) [요약] https://help.figma.com/hc/en-us/articles/20774752502935

### 테스트 케이스

- 정의: "A set of preconditions, inputs, actions, expected results and postconditions, developed based on test conditions" [원문] https://glossary.istqb.org/en_US/term/test-case
- IEEE 829-2008은 폐지(Superseded), ISO/IEC/IEEE 29119-3:2021이 테스트 문서 템플릿 표준 [요약] https://standards.ieee.org/ieee/829/3787/ , [원문—초록] https://www.iso.org/standard/79429.html
- 인수 조건 → 테스트 케이스(ATDD) [원문] ISTQB §4.5.3: 구현 전 고객·개발자·테스터가 함께 만든다 / 긍정 → 부정 → 비기능 순 / 이해관계자가 읽을 수 있는 자연어 / 스토리를 다 덮되 넘지 않고, 두 케이스가 같은 특성을 중복하지 않는다

### 추적성

- 추적 매트릭스(RTM): 산출물 사이를 연결해 커버리지를 판단하는 표 [원문] https://glossary.istqb.org/en_US/term/traceability-matrix
- 효과: 요구사항이 테스트로 덮였는지 검증, **변경 영향 판단**, 감사 지원, 이해관계자의 보고서 이해 [원문] ISTQB §1.4.4
- 방향: 사전 추적(요구사항 → 출처: 누가 요청했나) / 사후 추적(요구사항 → 설계·테스트·결과). 산출물이 수천 개면 표보다 그래프가 낫다 [요약—위키] https://en.wikipedia.org/wiki/Requirements_traceability

### 요구사항 소통이 실패하는 곳 — NaPiRE (10개국 228개 조직) [요약] https://arxiv.org/abs/1611.10288

| 문제 | 언급 조직 | 실패 원인 지목 |

- 원인: 시간 부족 18%, RE 담당자 경험 부족 18%, 자격 부족 14%, 고객 소통 결함 13%, 요구가 추상적으로 남음 13%
- 결과: 일정 초과, 구현 후 재작업, 품질 저하, 고객 불만

**모호성에 대한 반대 증거**
- 산업 프로젝트 40건: 모호성 수준은 성공과 상관이 없었고 테스트 단계 결함도 늘리지 않았다 — Philippo 외, REFSQ 2013 [원문—초록] https://link.springer.com/chapter/10.1007/978-3-642-37422-7_5
- 25명 실험: 수동태는 영향이 미미, **모호한 대명사는 잘못된 연관을 강하게 유발** — Frattini 외 [요약] https://arxiv.org/abs/2401.01154
- 요구 품질 규칙 연구는 규범에 치우쳐 후속 개발에 미치는 영향과 연결이 약하다 — Frattini 외 [요약] https://arxiv.org/abs/2309.10355

### 무엇이 이해를 높이나

- 그림 vs 글: 28명 실험에서 정확도 차이 유의하지 않음, 그림이 시간·시각 노력 더 듦(훈련하면 개선) — Sharafi 외, ICPC 2013 [요약] https://www.ptidej.net/downloads/replications/icpc13a/
- EARS: 항공 엔진 제어 요구 사례에서 질적·양적 개선 보고(수치 미확인) — Mavin 외, RE 2009 [원문—초록] https://ieeexplore.ieee.org/document/5328509

- 예시 중심 명세(BDD)·용어집·"범위 밖"·가정 명시의 이해도 효과를 측정한 연구는 찾지 못했다

## 5. 설계에 주는 뜻 (사실만, 두 조사 종합)

1. 가장 많이 보고된 실패는 문장의 모호함이 아니라 **빠진 요구(48%)와 소통 결함(41%)**, 그리고 **요구 변경(33%)**이다
2. 모호성 전반은 성공과 상관이 확인되지 않았고, 결함 종류별 영향이 다르다(모호한 대명사 강함, 수동태 미미)
3. 조사한 PRD 템플릿 대부분에 **"하지 않는 것"과 "열린 질문"** 섹션이 있다. Spec Kit은 미확정을 `[NEEDS CLARIFICATION]`으로 표시한다
4. **인수 조건 = 테스트 조건**(ISTQB). 테스트 케이스는 인수 조건에서 1:N으로 도출하고, 중복·범위 초과 금지 규칙이 있다
5. 에이전트용 도구들은 공통으로 **무엇·왜와 어떻게를 분리**하고, 수용 기준(Given/When/Then 또는 EARS)·가정·미확정 표시를 둔다
6. 한국 화면설계서 관행은 **화면 ID를 참조 단위**로 쓰고 변경 이력·삭제 흔적을 남긴다. 실무 불만의 공통점은 **예외 상태 미정의와 명칭·식별자 불일치**다
7. QA 쪽의 확인된 실패는 **변경이 전달되지 않는 것**이고, ISTQB는 추적성의 효과로 변경 영향 판단을 든다
8. 그림이 글보다 정확도를 높인다는 근거는 없고, 분량이 큰 명세가 항상 낫지 않으며, **긴 생성 명세는 사람이 읽지 않게 된다**는 실태 근거가 있다
9. 여러 역할이 한 문서에서 서로 다른 것을 찾는다는 문제 제기와 "역할별 뷰" 제안이 있다(RE 2012)
10. Atlassian은 착수 전 전원 사인오프와 갱신 통지 부재를 안티패턴으로 든다 — 승인 기능은 이 지적과 긴장 관계에 있다
