# "Agent OS" 리서치 — 정의와 구성요소 (조사일 2026-11-21)

경로: ego-browser 6라운드(구글 검색·페이지 직독, task space 1개, 종료함) + arXiv API(curl) 3회 + gh 2회 + WebFetch 약 40회 + 공식 문서 curl/grep. agy는 쓰지 않았다(ego-browser로 충분했음).

읽는 법
- 모든 주장에 URL과 게시일/갱신일을 붙였다. 날짜가 페이지에 없으면 "날짜 없음(접근 2026-11-21)"이라고 적었다.
- 논문 4편(2606.01508, 2608.03214, 2609.29647, 2606.20683)은 **초록만** 확인했다(HTML 404 또는 시간 제약). 표에서 이 행의 Y는 초록에 적힌 범위까지만이다.
- 인용부호(" ")는 원문(또는 WebFetch가 돌려준 원문 발췌)에서 확인한 문구에만 썼다. WebFetch는 소형 모델이 요약해 주는 도구라서, 결정적인 인용은 원문에서 다시 확인하는 것이 좋다.
- 웹 페이지 안에 에이전트를 향한 지시문(프롬프트 인젝션)은 발견되지 않았다.

## 2. 구성요소별 구현 방식 (선도 소스 2~3개)

### 2-0. 참고: IBM의 "OS 대응표" (R4, 2026-07-27)
설계를 점검할 체크리스트로 가장 쓸 만한 연구 자료다. Table I은 각 primitive를 고전 OS와 Cloud OS(Kubernetes)의 대응물에 맞춰 놓았다(WebFetch로 확인).
Agent lifecycle↔Process/Pod, Orchestrator(스케줄링, token-budget quota)↔Scheduler/kube-scheduler, Skills registry↔패키지 매니저/Helm, Tool mediation↔system call/sidecar, Context management↔virtual memory/ResourceQuota, A2A↔IPC/Service, Agent memory↔file system/PV·etcd, Identity & authorization↔ACL/RBAC, Behavioral guardrails↔MAC(SELinux)/OPA, Failure detection↔signal/liveness probe, Saga & checkpoint↔transaction·journal/Temporal, Trajectory observability↔audit·syslog/Prometheus·Jaeger, AI-aware proxy↔network stack/Envoy.
- 예산은 Orchestrator primitive 안에 "multi-dimensional" quota(토큰, 도구 호출, 시간, 비용)로 들어 있다.
- 코드 실행 샌드박스는 IV-L절에서 다루지만(seccomp-BPF, namespaces, copy-on-write staging) 표에는 빠져 있다.
- 평가(eval)는 primitive로 들지 않았다.

### 2-1. 워크플로/그래프 정의
- **LangGraph**: StateGraph의 노드와 엣지로 정의하고 `builder.compile(checkpointer=…, store=…)`로 컴파일한다. https://docs.langchain.com/oss/python/langgraph/persistence (접근 2026-11-21)
- **Google ADK**: "Graph Workflows"와 함께 Sequential / Loop / Parallel workflow agent를 제공한다. https://adk.dev/
- **Microsoft Agent Framework**: "Functional and graph-based workflows that connect agents and functions through explicit execution paths". 공식 문서에는 "If you can write a function to handle the task, do that instead of using an AI agent"라는 문구도 있다(overview, ms.date 2026-10-23).
- **CrewAI**: Flows(상태와 이벤트 기반 제어 흐름)가 Crews(자율 에이전트 팀)에게 일을 맡기는 2층 구조다.
- 흐름: 2026년 들어 그래프 대신 **"harness"**(모델 루프 + 도구 + 컨텍스트 압축) 방식이 늘었다. MAF Harness Agent, Claude Managed Agents, AgentCore Harness, Foundry "Microsoft Copilot harness"(preview)가 여기에 해당한다. OpenAI는 시각적 워크플로 빌더인 Agent Builder를 2026-11-30에 종료한다고 공지했다(AgentKit 페이지의 2026-06-03 업데이트).

### 2-2. 스케줄러/큐
- **AIOS**: Scheduler 하나가 모든 큐를 관리하며 FIFO와 Round Robin을 쓴다. RR의 time slice는 Context Manager의 스냅샷/복원(생성 중단과 재개)으로 구현한다(v5 HTML).
- **LangSmith Agent Server**: "Task queue"(몰려드는 요청 처리), "Crons", "double-texting"(실행 중에 새 입력이 들어오는 경우 처리).
- **Claude Managed Agents / Letta**: cron 기반 "scheduled deployments", 에이전트가 스스로 만드는 "Schedules".
- 관련 연구: "The Irreversibility Budget"(2026-08-31, https://arxiv.org/abs/2609.00275)은 admission control(실행 허가 판단)을 에이전트 OS의 스케줄러 책임으로 본다(아래 2-11절).

### 2-3. 메모리 (단기 / 장기 / 공유)
- **LangGraph**: 단기 메모리 = thread 단위 checkpointer(`thread_id`), 장기 메모리 = 여러 thread가 공유하는 Store. 서버판에서는 "Memory Store: Semantic search for long-term memories".
- **AWS AgentCore Memory**: short-term은 세션별 raw event(sessionId), long-term은 비동기로 추출하는 "memory strategies". 여러 에이전트가 memory store를 공유할 수 있다. 참고로 Runtime microVM의 메모리는 기본적으로 휘발성이다("By default, the compute (microVM) associated with a session is ephemeral").
- **Letta / MemGPT**: MemGPT는 main context(working context + FIFO queue)와 external context(recall storage, archival storage)로 나누고, "memory pressure warning"이 오면 축출한다. 현재 Letta는 git으로 버전 관리하는 MemFS, 여러 대화가 공유하는 메모리, 백그라운드 "dreaming"(sleep-time subagent)으로 바뀌었다.
- **CrewAI**: short-term / long-term / entity / external로 나뉘던 메모리를 단일 `Memory` 클래스로 합쳤다. 저장할 때 LLM이 scope·category·importance를 추론하고, 검색할 때 유사도·최신성·중요도를 섞어 점수를 매긴다.
- **Google**: Agent Platform Sessions(Custom Session ID) + Memory Bank("dynamically generates and curates long-term memories").

### 2-4. 도구 레지스트리와 권한
- **Windows**: On-device registry(ODR)에 agent connector(MCP 서버)를 등록하고, MCP proxy가 "authentication, authorization, and auditing"을 맡는다. Intune/GPO로 커넥터를 켜고 끈다(2025-11-18).
- **AWS AgentCore**: Gateway가 API·Lambda를 MCP 도구로 바꿔 주고, Registry가 에이전트·MCP 서버·skill을 등록하고 승인하는 흐름을 관리한다. Policy는 Gateway에서 "intercept every tool call before execution". 정책 언어는 Policy 페이지에서는 Cedar, 개요 페이지에서는 Cedar 호환 "Dogwood"라고 되어 있어 **문서끼리 불일치**한다.
- **Foundry Toolboxes**: 도구를 한 번 골라 묶어 두면 "single managed MCP endpoint"로 노출되고, 인증·거버넌스·버전 관리가 한곳에 모인다. 새 버전을 만들어 테스트한 뒤 기본값으로 승격하는 방식이다.
- **Claude Agent SDK**: 다음 순서로 평가한다. hook(PreToolUse가 deny를 반환할 수 있음) → deny 규칙 → permission mode → allow 규칙 → `canUseTool` 콜백. hook이 allow를 반환해도 deny·ask 규칙은 그대로 평가된다.
- **OpenAI AgentKit Connector Registry**: "a central place for admins to manage how data and tools connect across OpenAI products"(beta).

### 2-5. 에이전트 신원/인증
- **Microsoft**: Foundry는 에이전트마다 전용 Entra identity를 주고 OBO(On-Behalf-Of) passthrough를 지원하며, Entra Agent Registry에 게시한다. Windows는 agent account / Agent ID로 사용자 행동과 에이전트 행동을 구분한다.
- **AWS AgentCore Identity**: "Agent identities are implemented as workload identities with specialized attributes". Cognito, Okta, Entra 같은 기존 IdP와 함께 쓴다.
- **Google Agent Identity**: "every agent receives a unique cryptographic ID"를 authorization policy에 매핑한다(2026-04-23). SPIFFE를 쓰는지는 확인하지 못했다.
- **Claude Managed Agents**: 신원보다는 자격증명 격리에 가깝다. MCP 호출은 세션 범위 토큰을 받은 proxy가 vault에서 자격증명을 가져오는 구조이고, "The harness is never made aware of any credentials".
- **A2A**: Agent Card에 securitySchemes(API key, HTTP, OAuth2, OIDC, mTLS)를 선언한다.

### 2-6. 사람 승인(HITL) 체크포인트
- **LangGraph**: 노드 안에서 `interrupt(payload)`를 부르면 실행이 멈추고, `Command(resume=…)`의 값이 `interrupt()`의 반환값이 된다. 상태는 checkpointer가 저장하며, 운영 환경에서는 "use a durable checkpointer in production".
- **OpenAI Agents SDK**: 도구에 `needs_approval`을 걸면 실행 결과에 `interruptions`가 담기고, `result.to_state()` → `state.approve(...)` → `Runner.run(agent, state)`로 재개한다. RunState는 직렬화해서 나중에 재개할 수 있다.
- **A2A**: 태스크 상태 `TASK_STATE_INPUT_REQUIRED`와 `TASK_STATE_AUTH_REQUIRED`가 "interrupted state"로 정의돼 있어, 에이전트 사이에서도 HITL이 프로토콜 수준에서 표현된다.
- **MCP**: 클라이언트 기능 Elicitation(서버가 사용자에게 추가 정보를 요청)과 "Hosts must obtain explicit user consent before invoking any tool"(보안 원칙).
- **AIOS**: Access Manager의 user intervention interface가 삭제·덮어쓰기 같은 되돌릴 수 없는 작업 전에 확인을 받는다.
- 기타: ADK "Action confirmations", CrewAI `@human_feedback`, MAF "don't-ask-again tool approval".

### 2-7. 가드레일/정책
- **OpenAI Agents SDK**: input / output / tool guardrail을 두고, `tripwire_triggered`가 되면 예외를 던진다. tool guardrail은 함수 도구 호출마다(MCP 포함) 실행 전후에 돈다.
- **AWS AgentCore Policy**: 정책을 자연어나 Cedar 계열 언어로 쓰는 "deterministic control"이며, Gateway에서 모든 도구 호출에 적용된다.
- **Google Agent Gateway + Model Armor**: "air traffic control for your agent ecosystem". 프롬프트 인젝션과 데이터 유출을 막는다. 여기에 Agent Anomaly Detection(통계 모델 + LLM-as-a-judge)이 더해진다.
- **Windows MXC**: 에이전트별 파일·네트워크 정책을 런타임에 강제한다. "learning and permissive modes"로 먼저 관찰한 뒤 강제로 넘어갈 수 있다(GA, 2026-11-17).
- **Salesforce**: Agent Script로 결정적 로직과 LLM 추론을 섞는다("hybrid reasoning"). 여기에 Trusted Services(Einstein Trust Layer)가 붙는다.

### 2-8. 관측성/트레이싱
- **AWS AgentCore Observability**: OTEL 호환 텔레메트리를 CloudWatch로 보낸다. Evaluations와 Optimization도 같은 trace를 입력으로 쓴다.
- **Microsoft**: MAF의 OpenTelemetryAgent middleware가 trace를 Application Insights로 보낸다. Foundry는 "Inspect every model call, tool invocation, and decision".
- **OpenAI Agents SDK**: 기본으로 켜진 tracing(trace/span, custom processor, 내보내기 전 redaction). trace는 OpenAI evals·fine-tuning에도 쓸 수 있다.
- **Claude Managed Agents**: session 이벤트 로그 전체를 가져올 수 있다(`getEvents()`). 별도 트레이싱 제품은 확인하지 못했다.

### 2-9. 평가
- **AWS AgentCore Evaluations**(2026-03 GA): session·trace·span 단위로 평가한다(Strands/LangGraph, OTEL/OpenInference 계측).
- **Google**: Agent Simulation(합성 사용자 대화) + Agent Evaluation("multi-turn autoraters") + Agent Optimizer.
- **Salesforce**: Batch Testing, Custom Scorers, Task Resolution metric(Dreamforce 2026).
- **OpenAI**: Evals의 trace grading을 제공했지만 **2026-11-30 종료가 공지돼 있다**. 플랫폼 평가 기능에 기대는 설계라면 벤더 종속 위험이 있다는 실례다.
- Foundry, AgentCore, Google 세 곳 모두 "평가 → 자동 최적화(지시문·도구 설명 개선, A/B)"를 2026년에 추가했다.

### 2-10. 멀티테넌트/세션 격리
- **AWS AgentCore Runtime**: "Each session … receives its own dedicated microVM with isolated compute, memory, and filesystem". 세션은 microVM에서 최대 8시간, Instances에서 최대 14일 유지되고, 기본 15분 동안 활동이 없으면 정지한다.
- **Foundry hosted agents**: BYO VNet에서 "each session runs in a VM-isolated sandbox". 대화 상태는 BYO Cosmos DB에 둘 수 있다.
- **Windows**: process/session container → WSL container → VM → Windows 365 for Agents → (실험) local Micro VM 순으로 격리 강도가 올라간다.
- **Claude Managed Agents**: Anthropic이 관리하는 sandbox, 자체 호스팅 sandbox, 서비스 전체 자체 호스팅 중에서 고른다. harness를 컨테이너 밖으로 빼서 "컨테이너 장애가 도구 호출 오류로 바뀌게" 했다.
- 연구: Aegis OS(2026-10-22, https://arxiv.org/abs/2611.08516)가 "Transactional Multi-Tenant Operating System Runtime"을 제안했다(제목만 확인).

### 2-11. 비용/예산 통제 — 다루는 소스가 가장 적은 영역
- **Claude Agent SDK**: `maxBudgetUsd`("Stop the query when the client-side cost estimate reaches this USD value"), `maxTurns`, 결과에 담기는 `total_cost_usd`(클라이언트 쪽 추정값이라 실제 청구액과 다를 수 있음).
- **OpenAI Agents SDK**: `max_turns`만 있다(초과하면 `MaxTurnsExceeded`). 금액 예산 기능은 확인하지 못했다.
- **IBM R4**: orchestrator가 토큰·도구 호출·시간·비용의 다차원 quota를 관리한다.
- **AWS AgentCore Payments**: 에이전트가 쓰는 결제에 "configurable spending limits"를 건다(x402/MPP). LLM 토큰 예산이 아니라 결제 한도다.
- **한국**: LG CNS Router(성능·비용을 보고 모델 자동 선택), 삼성SDS FabriX 2.0("사용량과 비용…관리").
- **Irreversibility Budget**(2026-08-31): 테넌트별로 "되돌릴 수 없는 영향"의 누적 위험을 예산으로 관리하자는 논문이다. 개별 게이트만 둘 때는 테넌트 위험 한도를 최대 48배 넘었다고 보고했다(초록).

### 2-12. 에이전트 간·도구 프로토콜
- **MCP**(2026-07-28판): JSON-RPC 2.0. 서버 기능은 Tools/Resources/Prompts, 클라이언트 기능은 Elicitation이다. 확장으로 Tasks(장기 실행, 폴링, "durable handles"), Skills over MCP, MCP Apps가 있다. 이번 판의 개요에는 클라이언트 기능으로 Elicitation만 나온다(이전 판의 sampling·roots가 빠졌는지는 확인하지 못함).
- **A2A v1.0**: Agent Card, Task 생명주기, JSON-RPC / gRPC / HTTP+JSON 바인딩, push notification(webhook), streaming을 정의한다. 2026-08-17에 AAIF("hosted by the Linux Foundation")에 합류했고, AAIF에는 MCP·goose·AGENTS.md·agentgateway도 들어 있다.
- 채택 현황: Foundry(A2A v1.0 GA), AgentCore Runtime(MCP·A2A), ADK(A2A), Agentforce(hosted MCP server, A2A 호환 orchestration), LangSmith Agent Server와 Agno(MCP/A2A endpoint), LG CNS(MCP·A2A). MCP는 30개 행 가운데 사실상 전부가 지원하고, A2A는 클라우드와 엔터프라이즈 플랫폼 중심이다.

### 2-13. 내구 실행/재개
- **Claude Managed Agents**: session을 harness 밖에 있는 "append-only log"로 둔다. harness가 죽으면 `wake(sessionId)` → `getSession(id)` → 마지막 이벤트부터 이어서 실행하고, `emitEvent(id, event)`로 기록한다. 이렇게 분리하자 p50 TTFT가 약 60%, p95가 90% 넘게 줄었다고 한다(2026-04-08).
- **LangGraph**: 매 step checkpoint를 남기고 thread_id로 다시 불러온다. 오류 상태에서도 재개할 수 있다("resume later, even when in an error state").
- **CrewAI Checkpointing**: 이벤트(`task_completed` 기본, `llm_call_completed` 선택)가 일어날 때 스냅샷을 쓴다. 재개하면 완료된 task는 건너뛰고, fork하면 새 lineage가 생긴다. 저장소는 Json/Sqlite provider.
- **OpenAI Agents SDK**: RunState 직렬화, `cancel(mode="after_turn")` 후 재개, Sandbox agents의 "resumable sessions".
- **IBM R4**: "Saga and checkpoint"(↔ transaction/journal, Temporal). 부수효과(side effect)의 보상(compensation)까지 다룬다는 점이 다른 소스와 다르다.

## 3. 합의된 핵심 vs 소수만 언급하는 것

### 합의된 핵심 (30개 소스 중 2/3 이상, 런타임 14개 중 N이 0~1개)
1. **도구 레지스트리 + 호출 단위 권한 게이트**(29/30). 2026년의 공통 형태는 "레지스트리(카탈로그·승인 흐름) + 프록시/게이트웨이(모든 도구 호출을 가로채 인증·정책·감사)"다. Windows MCP proxy, AgentCore Gateway+Policy, Google Agent Gateway, Foundry Toolboxes가 그렇다.
2. **가드레일/정책**(25/30). 입력·출력·도구 호출의 세 지점에 둔다. 클라우드는 "결정적(deterministic) 정책 엔진"(Cedar 계열, MXC 정책)을 LLM 기반 필터와 함께 쓰는 쪽으로 가고 있다.
3. **MCP(도구) + A2A(에이전트 간)**(23/30). MCP는 사실상 표준이 됐고, A2A는 2026-08에 AAIF로 들어오면서 엔터프라이즈 플랫폼에서 빠르게 채택되고 있다.
4. **메모리 2층(세션/thread 단기 + 세션을 넘는 장기, 공유 가능)**(22/30).
5. **내구 실행/재개**(20/30, 런타임 14개 중 N 2개). checkpoint 또는 이벤트 로그로 구현하고, thread/session ID로 다시 붙는다.
6. **관측성(트레이싱)**과 **HITL 승인**. 런타임 14개 중 N이 0개다(30개 전체 집계가 낮은 것은 프로토콜·논문·한국 보도자료에서 "?"가 많기 때문). 트레이싱은 OpenTelemetry로 수렴하고 있다.

### 플랫폼급에서만 등장 (클라우드·OS 벤더는 강조하고 SDK는 뺌)
- **에이전트 신원**(19/30): Microsoft, Google, AWS, OpenAI Frontier, Windows, AgentKernel, IBM에 있고, SDK(OpenAI SDK, Claude SDK, ADK, CrewAI, MAF)에는 없다. "사람 신원과 분리된 에이전트 전용 신원"이 엔터프라이즈 플랫폼들의 공통 요구다.
- **평가**(13/30): AWS, Google, Microsoft, Salesforce, LG CNS에 있다. AIOS 같은 연구 OS 계열과 IBM primitive 표에는 없다.
- **세션 격리**(14/30): 호스팅 런타임(AgentCore microVM, Foundry VM sandbox, Managed Agents, Windows MXC)만 Y다.

### 소수만 언급
- **스케줄러/큐**(9/30): AIOS, IBM, R5·R6 논문, LangSmith Agent Server, Letta, Managed Agents(cron), Agno. 대부분의 벤더는 "autoscale"로 덮고 공정 스케줄링을 이름 붙여 다루지 않는다. 연구 쪽 "OS" 논문은 이것을 핵심으로 본다는 점이 업계와 가장 크게 다르다.
- **비용/예산 통제**(9/30): Claude SDK `maxBudgetUsd`, IBM quota, AgentCore Payments 한도, LG CNS Router, 삼성SDS FabriX, Irreversibility Budget 논문. **대부분의 플랫폼에 금액 예산 차단 기능이 없다.** 그래서 직접 구현해야 할 가능성이 가장 높은 항목이다.
- **사가/보상 트랜잭션**: IBM만 명시한다.
- **레지스트리 승인 워크플로**(게시 → 검토 → 승인): AWS Registry, Google Agent Registry, Foundry 게시, 카카오 "등록·검증"에 있다.

### 소형 멀티에이전트 제품용 비교 체크리스트 (위 근거를 요약한 것)
- [ ] 도구 호출마다 거치는 단일 게이트(허용/거부 규칙 + 승인 콜백 + 감사 로그)가 있는가 — Claude SDK 권한 평가 순서, AgentCore Policy 참고
- [ ] 입력·출력·도구 단의 가드레일, 그리고 그중 결정적 규칙이 무엇인가
- [ ] thread/session ID 기반 단기 상태와 세션을 넘는 장기 메모리를 분리했는가. 에이전트 사이 공유 범위를 정했는가
- [ ] 실행이 중간에 죽어도 checkpoint나 이벤트 로그에서 재개되는가. 부수효과는 멱등인가, 아니면 보상 가능한가
- [ ] 사람 승인이 "일시정지 → 상태 직렬화 → 승인 → 재개" 흐름으로 되는가(LangGraph interrupt, OpenAI RunState)
- [ ] OTel 호환 trace가 남는가(모델 호출·도구 호출·에이전트 간 위임을 span으로)
- [ ] 에이전트 간 위임 인터페이스가 A2A의 Task 상태 모델(INPUT_REQUIRED/AUTH_REQUIRED)과 호환되는가, 도구는 MCP인가
- [ ] 에이전트별 신원/자격증명을 사람 계정과 분리했는가. 자격증명이 모델 컨텍스트에 들어가지 않는가(Managed Agents vault 패턴)
- [ ] 실행 단위(세션/테넌트) 격리 수준(프로세스 / 컨테이너 / microVM)

## 4. 용어 주의 — "Agent OS"는 정착된 용어인가?

**결론: 연구에서는 실제로 이어지는 흐름이 있지만 정의가 합의되지 않은 "비유적 프레이밍"이고, 업계에서는 주로 제품명과 마케팅 라벨이다. 큰 플랫폼 벤더들은 1차 문서에서 이 말을 피하고 "agent runtime / agent platform / harness / control plane"이라고 부른다.**

근거
1. **연구 쪽 계보는 있다**: MemGPT "Towards LLMs as Operating Systems"(2023-10) → AIOS(2024-03, cs.OS, v5 2025-08) → KAOS(2024-06) → 2026년에 논문이 몰려 나왔다. arXiv에서 "agent operating system"을 검색하면 2026년에만 AOS 두 편, AgentKernel, IBM, Irreversibility Budget, MatOS, Mako, TopoClaw, ABot-AgentOS, Emergi-PersonaOS 등이 나온다(arXiv API 조회, 2026-11-21).
2. **그런데 정의가 서로 다르다**: 같은 "Agent Operating System (AOS)"라는 이름 아래 2606.01508은 "기존 OS에 통합되는 agentic control plane"을, 2608.03214는 "Linux·Windows·컨테이너는 경계 밖에 두는 vendor-neutral reference architecture"를 말한다. 한쪽은 OS 안으로 들어가고 다른 쪽은 OS 밖에 머문다. 2603.08938 "AgentOS"는 GUI를 대체하는 개인용 NUI OS이고, UFO2 "Desktop AgentOS"(2504.14603)는 Windows 데스크톱 에이전트다. 같은 단어가 서로 다른 계층을 가리킨다.
3. **IBM 논문이 합의가 없다고 직접 말한다**: "dozens of frameworks and protocols have emerged, but no community consensus exists on what the core abstractions are or what guarantees they carry"(2607.25076 초록, 2026-07-27). 그러면서 POSIX나 Kubernetes처럼 공통 추상화로 모일 필요가 있다고 주장한다.
4. **대형 벤더의 1차 문서는 "OS"를 쓰지 않는다** (모두 원문에서 확인)
   - AWS AgentCore: "an agentic platform"
   - Google: "Gemini Enterprise Agent Platform", "the evolution of Vertex AI"
   - OpenAI Frontier: "a new platform". "operating system"이라는 말은 없다
   - Microsoft Foundry: "a managed platform"
   - Salesforce Agentforce 360 플랫폼 페이지와 Dreamforce 2026 발표: "operating system" 없음
   - Anthropic Managed Agents 글: OS를 **설계 비유**로만 쓴다. 프로세스나 파일처럼 "outlasted the hardware" 하는 안정된 인터페이스를 만들자는 취지
5. **Windows는 사례가 엇갈린다**: Windows 책임자 Pavan Davuluri가 X에서 "agentic OS" 계획을 밝히자 수백 개의 반발 댓글이 달렸고, 댓글은 며칠 뒤 잠겼다(The Verge, 2025-11-21 KST, https://www.theverge.com/tech/825022/microsoft-windows-40-year-anniversary-agentic-os-future). 그러나 같은 시기 Windows 공식 개발자 블로그는 "native agent infrastructure"라고 썼고, Ignite 2026 블로그(2026-11-17)는 "the OS for hybrid intelligence"라고 썼다. 공식 문서에서는 "agentic OS"를 쓰지 않았다(WebFetch 확인).
6. **"Agent OS"를 제품명으로 쓰는 곳**: PwC "agent OS"(2025-03-27, "enterprise AI command center", 실제 내용은 오케스트레이션과 통합 계층), Agno "AgentOS"("the FastAPI for agents", 실제 내용은 런타임 서버), 한컴 "소버린 에이전틱 OS"(2026-05 사명 변경과 함께 선언, 2026-06 베타, 2027 상반기 정식 출시 목표 — **아직 계획 단계**). 이 밖에 검색 상위는 SEO성 해설 블로그가 차지한다(pancake.ai, markovate 등).
7. **한국 대기업은 대부분 "플랫폼"이라고 부른다**: 삼성SDS(FabriX, CES 2026 보도자료와 2026-10 기사 모두 OS라는 말 없음), LG CNS(AgenticWorks, 페이지에 OS라는 말 없음), 카카오("플랫폼"/"마켓플레이스"), 업스테이지, 네이버 모두 확인한 자료에서는 'OS'를 쓰지 않았다. 한컴만 예외다.

실무 시사점: 설계 문서에서 "Agent OS"라고 쓰려면 **어느 정의를 따르는지**(AIOS식 커널 서비스인지, IBM식 primitive 13개인지, 2608.03214식 2-plane인지)를 밝혀야 오해가 없다. 기능 비교에는 "runtime / control plane / harness" 같은 용어가 업계 문서와 바로 대응된다.
