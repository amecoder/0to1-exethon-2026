# 라이너 .EXE-THON 대회 조사와 구축 범위 검토 (2026-11-12)

- 앞선 문서: `docs/reports/2026-11-12_엑스톤_사전리서치.md`, `docs/plans/2026-11-12_엑스톤_신청_주제와_구현범위.md`
- 방법: Fable 모델 하위 에이전트 2개가 조사와 검토를 했다. 조사는 ego-browser와 WebFetch로 원문을 읽었다
- 표기: **확인** = 원문 텍스트를 직접 읽음 / **확인(요약)** = WebFetch 요약으로만 읽음 / **추정** = 원문 근거 없음
- 이 문서는 범위 **후보**를 순서 없이 적는다. 무엇을 고를지는 사용자가 정한다

## 0. 오늘 사용자가 밝힌 실제 동기

> 사업은 하고 싶고 뭐든 만들고 싶은데 문서도 못 만들고, 보고도 못 하고, 결국 개발자한테 말만 하고 개발해 달라고 하는 게 싫다. 이 부분을 보다 명확하고 투명하게 해서 개선하고 싶다.

**사용자는 개발자다(2026-11-12 사용자 확인).** 이 문장은 말로 요청을 **받는** 개발자의 고충이다.

| 역할 | 누구 |
|---|---|
| 불편을 겪는 사람 | 개발자 — 모호한 말 요청을 받아 매번 되묻고, 검토하고, 바뀐 내용을 다시 확인한다 |
| 요청하는 사람 | 사업을 하고 싶고 뭐든 만들고 싶지만 문서·보고서를 못 쓰는 사람(사업가·기획자·현업 담당자) |

신청서(계획 문서 0절)의 "개발자가 매번 문서를 검토하고 피드백해야 했습니다"와 같은 장면이다.

### 0-1. 페르소나 일반화 (2026-11-12 사용자 결정)

특정 직군으로 좁히지 않고 두 역할과 그 사이의 에이전트로 정의한다.

| 역할 | 정의 | 소프트웨어 개발에서 | 다른 업무에서 (예) |
|---|---|---|---|
| **시키는 사람** | 원하는 결과는 있지만 그것을 문서·조건으로 풀어 쓰지 못하는 사람 | 사업가·기획자·현업 | 팀장(보고서 지시), 가게 사장(외주 디자인 의뢰) |
| **하는 사람** | 그 요청을 받아 실제로 업무를 수행하는 사람 | 개발자·QA | 팀원(보고서 작성), 외주 디자이너 |
| **에이전트** | 둘 사이에서 최선을 다해 둘을 연결한다 | | |

에이전트가 연결하는 방향 (사용자 문장 "문서도 못 만들고, 보고도 못 하고"에서, 해석 포함):

- **시키는 사람 → 하는 사람**: 말로 된 요청을 질문으로 구체화해 하는 사람이 바로 쓸 수 있는 요청서(조건·완료 기준·예외)로 만든다 — "문서를 못 만드는" 문제
- **하는 사람 → 시키는 사람**: 하는 사람의 역질문·진행 상황·이견을 시키는 사람이 알아듣는 말로 바꿔 전한다 — "보고를 못 하는" 문제(해석: 보고가 오가지 않는 양방향 단절로 읽음)
- **둘 다**: 같은 기록(결정과 근거, 변경과 영향, 승인)을 본다 — "투명하게"

신청서는 소프트웨어 개발 문서(BRD·PRD·화면설계서·테스트 케이스)를 다룬다. 일반화한 페르소나는 심사 기준 「확장성과 임팩트(20%) — 다른 조직과 직무로 넓힐 수 있는가」에 직접 대응한다. **시연을 소프트웨어 개발로 할지 다른 업무로 할지는 미정**(미정 항목 9 「시연 소재」에 포함).

> 정정 기록: 이 문서 첫 판(같은 날 18:37)은 사용자를 "문서를 못 쓰는 사업가"로 거꾸로 읽고 5·7·8절을 썼다. 이 판에서 그 부분을 고쳤다.

## 1. 대회 규정 (출처: https://contests.liner.com/hackathon/exe-thon-2611/ , 규정 2026-11-02 시행, 전부 확인)

| 항목 | 배점 | 원문 기준 |
|---|---|---|
| 문제 정의 | 30% | 경험에서 나온 구체적인 병목인가. 누가, 언제, 얼마나 불편한지 분명한가 |

## 5. 신청서와 실제 동기 비교 (0절 정정 반영, 추론 포함)

### 맞는 곳 (신청서 0절 기준 사실)

- 신청서의 피해자는 "매번 문서를 검토하고 피드백해야 했던 개발자"다. 사용자의 실제 동기도 말 요청을 받는 개발자의 고충이다 → **주인공(불편을 겪는 사람)이 같다**
- "질문하여 구체화", "승인 이력과 의사결정 근거", "모두가 동일한 기준"은 "명확하게·투명하게"와 겹친다

### 신청서보다 실제 동기에서 더 뚜렷한 것 (추론)

| 신청서 | 실제 동기 |
|---|---|
| 문서는 있고 품질이 들쭉날쭉 | 문서조차 없고 말만 오는 경우까지 포함 |
| 요청자는 "담당자"(문서 역량 편차) | 요청자는 문서·보고를 못 쓰는 사업가·현업 — 편차의 가장 아래 |
| 기획자·개발자·QA 다자 협업 | 요청자와 개발자 2자 관계가 출발점 |

- 도구에 **입력하는 사람(요청자)**과 **이득을 보는 사람(개발자)**이 다르다. 데모와 기획서에서 둘을 구분해 보여 줘야 한다(추론)

### 기능별 기여도 — 개발자의 고충 기준 (추론)

| 기능 | 기여 | 이유 |
|---|---|---|
| ① 질문으로 구체화 | 직접 | 개발자가 하던 되묻기를 요청 단계에서 끝낸다 |
| ③ 정합성·누락 검증 | 직접 | 개발자가 매번 하던 검토(빠진 예외·완료 기준)를 대신한다 |
| ⑤ 변경 영향 | 직접 | 말로 바뀐 요청이 어디를 흔드는지 개발자가 다시 찾지 않아도 된다 |
| ④ 승인·이력·근거 | 직접 | "말로 그랬잖아" 대신 기록이 남는다 — 투명성 |
| ② 표준 문서 | 중간 | 개발자가 받는 형식이 일정해진다. 4종 전부가 필요한지는 미정 |
| ⑥ 코딩 에이전트 연계 | 중간 | 개발자가 AI 코딩 도구를 쓰면 바로 이득. 내보내기 파일 수준이면 저비용 |

- 주인공이 신청서와 같으므로 신청서와의 충돌 문제는 작다. 제출물이 "신청 내용을 보완한 기획서"라 요청자 쪽을 구체화하는 보완은 예정된 절차다(확인)

## 6. "명확하게"·"투명하게"를 제품 동작으로 (가상 소재: 동네 꽃집 주 1회 꽃 정기구독 앱)

**명확하게**
- 질문으로 구체화: "구독 일시정지 돼요?", "배송 실패하면 환불이에요, 재배송이에요?"처럼 선택지로 묻는다
- 모호어 잡기: "빨리 배송" → "주문 후 몇 시간 안인가요?" LLM이 모호함에 관대할 수 있어 규칙 사전을 함께 둔다(사전리서치 2절)
- 완료 기준: "REQ-07 일시정지: 다음 배송 48시간 전까지 가능, 그 이후 버튼 비활성"
- 개발자용 요청서 한 장: 요구사항 ID, 완료 기준, 예외, 아직 안 정한 것

**투명하게**
- 결정 로그: "D-03 환불 대신 재배송. 이유: 요청자(꽃집 사장) 답변(11-14). 근거: 검색 출처 2건"
- 추적 링크: 아이디어 발화 → REQ-07 → 화면 "구독 관리" → TC-12
- 변경 diff와 영향: "일시정지를 24시간 전으로" → REQ-07, 화면 1개, TC 2개, 알림 문구 1개가 바뀜
- 미결정 표시: AI가 임의로 채운 값은 "가정"으로 표시

## 7. MVP 후보 (순서 없음, 공수는 추정)

| 후보 | 데모 장면 | Liner 쓰는 곳 | 공수 | 주된 위험 |
|---|---|---|---|---|
