## 1. Liner API (공식 개발자 문서 직접 확인)

**설계에 주는 뜻(사실만)**
- 에이전트 본체를 Liner Model API로 두고, 리서치 도구로 Liner Search를 툴 콜링하면 **Model API와 Search 둘 다** 핵심 기능에 들어간다. 다른 LLM을 본체로 쓰고 Liner Search만 도구로 붙여도 대회 조건(하나 이상)은 충족한다
- MCP 호출 $2/1,000건 기준이면 크레딧 $200 중 검색 비용은 작다. **Model API 토큰 단가는 확인하지 못했다** — 크레딧 지급(11-12 18시 이후) 뒤 콘솔 Billing에서 확인

## 2. 요구사항 품질 검증 기준

- **ISO/IEC/IEEE 29148**은 개별 요구사항의 품질 특성 9가지를 정의한다. 검증 가능성(verifiable)은 "충족 여부를 증명하거나, 가능하면 측정할 수 있게 쓴 요구사항"으로 설명된다. 9가지 이름(필요성·적절성·명확성(비모호)·완전성·단일성·실현 가능성·검증 가능성·정확성·적합성)은 기억에 의존한 목록이라 표준 원문 확인이 필요하다
- **LLM으로 검증한 연구**
  - Lubos 외(RE 2024): 요구사항 하나를 품질 특성 하나에 대해 "만족/불만족 + 이유 + 개선 문장"으로 판정하게 했다. LLM이 프로젝트 범위를 알아야 한다는 한계를 지적 — [arXiv 2408.10886](https://arxiv.org/abs/2408.10886v1)
  - LLM-as-a-judge 연구(Springer, 2026): 도메인 맥락 없이 판정 가능한 3가지(비모호성·검증 가능성·단일성)에 집중, 요구사항 50건을 평가자 5명으로 검증. 점수가 입력의 명확도와 프롬프트 설계에 따라 흔들린다 — [Springer](https://link.springer.com/article/10.1007/s00766-026-00462-z)
  - QUARE(arXiv 2603.11890, 2026): 비모호성에서 사람 점수(약 3.7)가 LLM 판정자(약 4.2~4.4)보다 낮았다 → **LLM 판정자가 모호함에 관대할 수 있다**. 표 머리가 깨져 읽은 값이라 원문 확인 필요 — [arXiv PDF](https://arxiv.org/pdf/2603.11890)

**설계에 주는 뜻(사실만)**: 검증 단계는 품질 특성마다 따로 판정하게 하는 방식이 선행 연구에 있다. 모호성 판정은 LLM이 놓치기 쉬워 규칙 기반 점검(예: "적절히", "빠르게" 같은 모호어 사전)을 함께 둘 근거가 된다.

## 3. 비슷한 기존 도구 (명세 주도 개발, SDD)

| 도구 | 특징 | 출처 |
|---|---|---|
| GitHub Spec Kit | 명세 → 계획 → 작업 흐름. GitHub 별 13만 이상(리뷰 글 기준) | [augmentcode 비교](https://augmentcode.com/tools/best-spec-driven-development-tools) |
| OpenSpec | 오픈소스 SDD 프레임워크, 별 5.2만(2026-06, 리뷰 글 기준) | [Thoughtworks Radar](https://www.thoughtworks.com/radar/tools/openspec), [Jama 글](https://www.jamasoftware.com/?p=12276) |
| Kiro | 에이전트 IDE, EARS 요구사항 문법(정해진 문장 틀로 요구사항을 쓰는 방식)과 훅 | [hackernoon](https://hackernoon.com/8-best-spec-driven-development-tools-for-software-engineers-in-regulated-industries-2026) |
| Jama Connect | 요구사항·테스트·코드·승인을 잇는 추적 모델을 내세우는 상용 도구 | [Jama SDD](https://www.jamasoftware.com/solutions/artificial-intelligence/spec-driven-development/) |
| TracerKit 등 소형 | PRD 생성 → 계획 → 점검 | [dev.to](https://dev.to/helderberto/why-i-built-tracerkit-fmo) |

- 실무 글: 명세를 아무도 강제하지 않으면 명세가 없을 때와 같은 어긋남(drift)이 생긴다. AI는 추적의 기계적 부분에는 맞지만 "요구사항이 실제로 충족됐는가"의 최종 판정자로는 맞지 않는다 — [glukhov.org](https://glukhov.org/app-architecture/testing-architecture/specs-tests-code-traceability-ai-development/)
- **요구사항 변경의 하위 영향(문서·테스트)을 계산해 주는 도구는 이번 검색에서 확인되지 않았다.** Jama의 추적 모델이 가장 가깝지만 영향 분석 여부는 출처로 확인 못 함(벤더 주장은 검증 전)

**설계에 주는 뜻(사실만)**: 명세 생성·계획은 기존 도구가 많다. 신청서의 차별점으로 적은 "검증 + 사람 승인 + 변경 영향 추적" 가운데 **변경 영향 분석**이 이번 검색 범위에서는 빈자리였다.
